## 1. Background & Challenges

기존 ETL 파이프라인은 각 DAG에 설정된 Cron 시각을 기준으로 실행됐습니다. 실행 시점이 되어도 소스 데이터가 도착했는지, 업스트림 처리가 완료됐는지는 트리거 조건에 반영되지 않았습니다. 데이터가 늦거나 누락된 상황에서도 하위 DAG가 실행될 수 있는 구조였습니다.

여러 DAG가 서로의 결과를 입력으로 사용하는 환경에서는 복구 작업도 복잡했습니다. 누락된 데이터를 업스트림에서 다시 처리한 뒤, 운영자가 영향받는 하위 DAG를 찾아 의존 순서에 맞춰 하나씩 재실행해야 했습니다.

메달리온 아키텍처를 도입하면서 계층 간 데이터 의존성을 실행 조건에도 반영할 필요가 생겼습니다. 목표는 **데이터가 준비된 뒤 다음 단계를 실행하고, 복구 시에도 같은 의존 관계를 따라 재처리가 이어지도록 만드는 것**이었습니다.

## 2. Architecture: As-Is vs To-Be

### As-Is Architecture

![각 DAG가 데이터 준비 여부와 무관하게 Cron으로 실행되고, 누락 복구 시 연관 DAG를 개별 재실행하는 구조](images/airflow-asset-as-is.svg)

1. **업스트림 실행:** 소스 데이터 준비 여부를 트리거 조건으로 확인하지 않고 설정된 Cron 시각에 실행했습니다.
2. **다운스트림 실행:** 업스트림의 처리 완료 여부와 관계없이 각 DAG의 Cron 스케줄에 따라 실행했습니다.
3. **장애 복구:** 누락 지점을 복구한 뒤, 연관된 하위 DAG를 운영자가 각각 수동으로 재실행했습니다.

### To-Be Architecture

![업스트림이 처리 대상 키 K를 포함한 Asset 이벤트를 발행하면 의존 조건을 충족한 하위 DAG가 해당 키를 기준으로 연쇄 실행되는 구조](images/airflow-asset-to-be.svg)

1. **업스트림 처리 및 이벤트 발행:** 데이터 처리 성공 시 해당 출력 Asset의 업데이트 이벤트에 처리 대상 Partition Key를 함께 전달합니다.
2. **키 기반 다운스트림 실행:** 하위 DAG는 Asset 의존 조건과 Partition Key를 기준으로 실행되어 입력 데이터의 처리 범위를 식별합니다.
3. **후속 처리 및 복구 전파:** 처리 결과를 다음 Asset 이벤트로 연결합니다. 장애 지점 상단의 업스트림 DAG를 재실행하면 의존 조건을 충족한 하위 DAG까지 재처리가 이어집니다.

그림의 A → B → C는 여러 DAG의 의존 관계를 단순화한 예시입니다. 여러 입력을 기다리는 DAG는 필요한 입력의 준비 조건도 충족해야 합니다. Asset 업데이트는 출력에 연결된 태스크의 성공을 기준으로 발생하므로, 이벤트를 발행하는 지점이 실제 데이터 처리 완료를 나타내도록 구성하는 것이 중요합니다. [Airflow Asset-Aware Scheduling](https://airflow.apache.org/docs/apache-airflow/stable/authoring-and-scheduling/asset-scheduling.html)

## 3. Solution & Technical Insights

### 1. 실행 시각에서 데이터 준비 상태로 트리거 전환

**[Issue]** Cron은 실행할 시각을 정하지만, 그 시각에 필요한 데이터가 준비됐는지까지 보장하지 않았습니다. 업스트림 지연이나 누락이 발생하면 하위 DAG의 실행과 실제 데이터 상태가 어긋났습니다.

**[Solution]** DAG 사이의 연결을 Dataset/Asset 업데이트 이벤트로 표현했습니다. 업스트림의 데이터 처리 결과가 다음 DAG의 실행 조건이 되도록 변경하여, 정기 배치에서 데이터 준비와 후속 실행을 연결했습니다.

### 2. 초기 Dataset/Asset 구조에서 드러난 백필의 한계

**[Issue]** Airflow 2의 Dataset과 Airflow 3 초기 Asset을 사용하던 시기에는 업스트림 실행 순서대로 다운스트림이 배치별로 한 번씩 실행될 것이라는 기대가 성립하지 않았습니다. 여러 업스트림 완료 이벤트가 쌓이면 다운스트림의 한 실행에서 여러 이벤트를 함께 소비하는 경우가 발생했습니다.

이는 이벤트의 도착 순서뿐 아니라 **업스트림의 배치 하나와 다운스트림 실행 하나가 일대일로 대응하지 않는 문제**였습니다. 공식 문서에서도 여러 Dataset을 기다리는 동안 특정 Dataset이 여러 번 업데이트되더라도, 조건이 충족되면 다운스트림은 한 번만 실행될 수 있다고 설명합니다. [Airflow 2.10.5 Data-aware scheduling](https://airflow.apache.org/docs/apache-airflow/2.10.5/authoring-and-scheduling/datasets.html)

운영 중 일정 간격을 두고 실행되는 정기 배치는 관찰한 범위에서 이벤트 지연 없이 이어졌습니다. 반면 여러 과거 배치를 연속으로 처리하는 백필에서는 이벤트가 한 실행에 묶여, 기존의 배치별 처리 범위와 멱등성 로직을 그대로 적용하기 어려웠습니다. 따라서 초기 전환 이후에도 백필은 수동으로 실행해야 했습니다.

**[Solution]** 후속 개선에서는 이벤트 수나 도착 순서로 처리 대상을 추론하는 대신, 각 이벤트가 어떤 데이터 입력 단위를 나타내는지 명시하는 방향을 선택했습니다. 이벤트 기반 트리거에 **처리 대상의 식별 기준**을 추가하는 것이 핵심이었습니다.

### 3. Partition Key로 정기 배치와 백필의 처리 기준 통일

**[Issue]** 다운스트림이 실행됐다는 사실만으로는 어떤 배치를 처리해야 하는지 충분히 설명할 수 없었습니다. 같은 데이터를 다시 처리할 때도 입력 범위를 안정적으로 식별할 기준이 필요했습니다.

**[Solution]** Airflow 3.3.2 적용 환경에서 Asset Partition Key를 활용해 데이터 입력의 기준 키를 이벤트에 함께 발행했습니다. 다운스트림은 이 키로 처리 대상을 식별할 수 있어, 정기 배치와 과거 데이터 재처리에 같은 기준을 적용하기 쉬워졌습니다.

예를 들어 서로 다른 배치의 키를 `K1`, `K2`라고 하면, 이벤트가 가까운 시점에 도착하더라도 다운스트림은 각 키가 가리키는 데이터 범위를 구분할 수 있습니다. `K1`을 재처리할 때도 동일한 입력 단위를 다시 지정할 수 있습니다. 이 예시는 처리 원리를 설명하기 위한 것으로 실제 키 형식이나 배치 주기를 뜻하지 않습니다.

Partition Key의 역할은 **처리 대상을 명확히 식별하는 것**입니다. 동일한 입력을 반복 처리해도 결과가 유지되는 멱등성은 해당 키를 사용하는 적재 로직까지 함께 충족해야 합니다. 키 도입으로 이 로직의 기준이 명확해졌으며, 이벤트 순서 보장에 의존하던 설계를 줄일 수 있었습니다.

## 4. Impact & Result

| 항목 | Cron 기반 | 초기 Dataset/Asset 전환 | Partition Key 적용 후 |
|---|---|---|---|
| 하위 DAG 실행 기준 | 개별 Cron 시각 | Asset 업데이트 조건 | Asset 업데이트 조건과 처리 대상 키 |
| 누락 데이터 복구 | 연관 DAG를 개별 수동 실행 | 이벤트 기반 후속 실행 도입 | 업스트림 재처리에서 하위 DAG로 연쇄 실행 |
| 백필 처리 | 수동 실행 | 이벤트 병합 문제로 수동 실행 유지 | 키를 전달해 배치별 처리 대상 식별 |
| 멱등성 구현 | DAG별 처리 범위 관리 | 한 실행에 여러 이벤트가 묶이면 처리 범위 해석이 복잡 | 키를 공통 기준으로 사용해 구현 단순화 |

장애 복구 시 운영자가 연관 DAG를 하나씩 실행하던 절차를 줄이고, 복구 시작점의 업스트림 DAG를 중심으로 재처리할 수 있게 됐습니다. 또한 Partition Key를 전달하면서 백필에서도 입력 단위를 명확히 식별할 수 있어, 멱등성 처리를 구현하기 쉬워졌습니다.

이 과정에서 얻은 설계 기준은 **“언제 실행할지”와 “어떤 데이터를 처리할지”를 함께 정의해야 한다**는 것입니다. Asset 이벤트로 실행 의존성을 표현하고, Partition Key로 처리 단위를 명시하면서 정기 배치뿐 아니라 장애 복구와 백필까지 이어지는 운영 구조를 만들었습니다.
