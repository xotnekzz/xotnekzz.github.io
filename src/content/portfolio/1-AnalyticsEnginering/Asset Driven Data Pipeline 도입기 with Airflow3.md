## 1. Background & Challenges

기존 ETL 파이프라인은 각 DAG에 설정된 Cron 시각을 기준으로 실행됐습니다. 실행 시점이 되어도 소스 데이터가 도착했는지, 업스트림 처리가 완료됐는지는 트리거 조건에 반영되지 않았습니다. 데이터가 늦거나 누락된 상황에서도 하위 DAG가 실행될 수 있는 구조였습니다.

여러 DAG가 서로의 결과를 입력으로 사용하는 환경에서는 복구 작업도 복잡했습니다. 누락된 데이터를 업스트림에서 다시 처리한 뒤, 운영자가 영향받는 하위 DAG를 찾아 의존 순서에 맞춰 하나씩 재실행해야 했습니다.

메달리온 아키텍처를 도입하면서 계층 간 데이터 의존성을 실행 조건에도 반영할 필요가 생겼습니다. 목표는 **데이터가 준비된 뒤 다음 단계를 실행하고, 복구 시에도 같은 의존 관계를 따라 재처리가 이어지도록 만드는 것**이었습니다.

## 2. Architecture: As-Is vs To-Be

### As-Is Architecture

![각 DAG가 데이터 준비 여부와 무관하게 Cron으로 실행되고, 누락 복구 시 연관 DAG를 개별 재실행하는 구조](images/airflow-asset-as-is.svg)

각 DAG는 데이터 준비·업스트림 완료 여부와 관계없이 Cron 시각에 실행됐고, 누락 복구 시 연관 하위 DAG를 운영자가 각각 재실행했습니다.

### To-Be Architecture

![업스트림이 처리 대상 키 K를 포함한 Asset 이벤트를 발행하면 의존 조건을 충족한 하위 DAG가 해당 키를 기준으로 연쇄 실행되는 구조](images/airflow-asset-to-be.svg)

업스트림 처리 성공 시 출력 Asset 이벤트에 Partition Key를 함께 발행합니다. 하위 DAG는 의존 조건과 키로 처리 범위를 식별하고, 결과를 다음 Asset 이벤트로 전달합니다. 업스트림 재실행은 조건을 충족한 하위 DAG의 재처리로 이어집니다.

그림의 A → B → C는 단순화한 예시입니다. 여러 입력을 쓰는 DAG는 모든 입력 준비 조건을 충족해야 하며, 이벤트 발행 지점은 실제 데이터 처리 완료를 나타내야 합니다.
## 3. Solution & Technical Insights

### 1. 실행 시각에서 데이터 준비 상태로 트리거 전환

**[Issue]** Cron은 실행할 시각을 정하지만, 그 시각에 필요한 데이터가 준비됐는지까지 보장하지 않았습니다. 업스트림 지연이나 누락이 발생하면 하위 DAG의 실행과 실제 데이터 상태가 어긋났습니다.

**[Solution]** DAG 사이의 연결을 Dataset/Asset 업데이트 이벤트로 표현했습니다. 업스트림의 데이터 처리 결과가 다음 DAG의 실행 조건이 되도록 변경하여, 정기 배치에서 데이터 준비와 후속 실행을 연결했습니다.

### 2. 초기 Dataset/Asset 구조에서 드러난 백필의 한계

**[Issue]** Airflow 2의 Dataset과 Airflow 3 초기 Asset을 사용하던 시기에는 업스트림 실행 순서대로 다운스트림이 배치별로 한 번씩 실행될 것이라는 기대가 성립하지 않았습니다. 여러 업스트림 완료 이벤트가 쌓이면 다운스트림의 한 실행에서 여러 이벤트를 함께 소비하는 경우가 발생했습니다.

이는 **업스트림 배치 하나와 다운스트림 실행 하나가 일대일로 대응하지 않는 문제**였습니다. 여러 과거 배치의 백필에서는 이벤트가 한 실행에 묶여 기존 처리 범위와 멱등성 로직을 적용하기 어려워, 초기 전환 후에도 백필은 수동 실행을 유지했습니다.

**[Solution]** 후속 개선에서는 이벤트 수나 도착 순서로 처리 대상을 추론하는 대신, 각 이벤트가 어떤 데이터 입력 단위를 나타내는지 명시하는 방향을 선택했습니다. 이벤트 기반 트리거에 **처리 대상의 식별 기준**을 추가하는 것이 핵심이었습니다.

### 3. Partition Key로 정기 배치와 백필의 처리 기준 통일

**[Issue]** 다운스트림이 실행됐다는 사실만으로는 어떤 배치를 처리해야 하는지 충분히 설명할 수 없었습니다. 같은 데이터를 다시 처리할 때도 입력 범위를 안정적으로 식별할 기준이 필요했습니다.

**[Solution]** Airflow 3.2.0에서 추가된 Asset Partition Key를 활용해 데이터 입력의 기준 키를 이벤트에 함께 발행했습니다. 다운스트림은 이 키로 처리 대상을 식별할 수 있어, 정기 배치와 과거 데이터 재처리에 같은 기준을 적용하기 쉬워졌습니다.

Partition Key는 **처리 대상을 명확히 식별**합니다. 같은 입력을 반복해도 결과를 유지하는 멱등성은 키를 사용하는 적재 로직까지 충족해야 하며, 키 도입으로 이벤트 순서에 의존하던 설계를 줄였습니다.
