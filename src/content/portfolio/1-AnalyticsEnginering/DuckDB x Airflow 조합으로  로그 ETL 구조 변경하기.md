## 1. Background & Challenges

사내 FortiGate 100E를 경유하는 1 Gbps 네트워크 경로가 게임 서비스와 로그 서비스 트래픽을 함께 수용하고 있었습니다. 피크타임에는 게임 서비스 장애와 로그 수집 누락이 빈번하게 발생했습니다.

Fluentd는 Nginx 로그를 실시간으로 변환했지만, TSV는 **1시간 동안 누적한 뒤 비압축 상태로 HDFS에 전송**했습니다. 실제 전달은 배치였고, 누적된 로그의 집중 전송이 공유 네트워크 부하를 키웠습니다.

HDFS의 TSV 기반 **Impala ETL 테이블**을 Airflow ETL로 처리해, **Parquet로 HDFS에 재저장한 운영 Impala 테이블**을 사용했습니다. 중간 TSV와 운영 Parquet의 이중 보관으로 저장 공간, 추가 읽기·쓰기 I/O, 두 테이블의 관리 비용이 발생했습니다.

로그 정규화 로직의 유지보수도 과제였습니다. Fluentd 구성에 포함된 GeoIP 데이터베이스 갱신이 제때 이루어지지 않았고, 2026년 1월 1~10일 운영 집계에서 국가 미식별 로그는 전체의 **1.8512%** 였습니다. 미식별 기준은 빈 문자열·NULL·`XX`이며, 개선 전에는 모두 빈 문자열로 기록됐습니다.

목표는 **배치 전송·중간 저장 부담을 줄이고, 변환 로직의 유지보수와 누락 데이터 재처리를 개선**하는 것이었습니다.

## 2. Architecture: As-Is vs To-Be

### As-Is Architecture

![공유 네트워크로 전송한 TSV를 HDFS의 Impala ETL 테이블로 저장하고, Airflow ETL을 거쳐 운영 Impala 테이블용 Parquet로 HDFS에 다시 저장하는 구조](images/fastlog-duckdb-as-is-impala.svg)

Nginx 로그를 Fluentd가 TSV로 변환한 뒤, 1시간분 비압축 파일을 공유 네트워크로 전송했습니다. HDFS의 TSV 기반 Impala ETL 테이블을 Airflow가 Parquet 운영 테이블로 다시 저장했습니다.

### To-Be Architecture

![시간 단위 gzip 원본을 SeaweedFS에 보관하고 Docker 기반 DuckDB ETL로 ZSTD Parquet를 생성한 뒤 실제 출력 파티션 정보를 Airflow에 전달하는 구조](images/fastlog-duckdb-to-be.svg)

Nginx 로그를 1시간 단위로 rotate·gzip해 SeaweedFS Filer에 원본으로 보관합니다. Airflow DockerOperator가 날짜·시간·서버별 DuckDB ETL을 실행해 ZSTD Parquet를 SeaweedFS S3에 저장하고, 실제 출력 파티션을 후속 DAG에 전달합니다.

ETL 컨테이너는 **입력 파일의 변환과 저장 결과 반환**, Airflow는 **실행 관리와 후속 DAG 연결**을 담당하도록 책임을 분리했습니다.

## 3. Solution & Technical Insights

### 1. 배치 전송 경계에서 압축하고, 원본과 분석 데이터의 역할 분리

**[Issue]** 비압축 TSV의 집중 전송이 서비스 트래픽과 경합했고, HDFS에서 TSV를 운영 Parquet로 재저장하며 중간 보관과 추가 I/O가 발생했습니다.

**[Solution]** 로그 서버에서 원본을 gzip으로 압축해 전송하고, **DuckDB가 Parquet를 직접 생성**하도록 변경했습니다. SeaweedFS에 재처리용 gzip 원본과 분석용 Parquet를 보관하면서, **비압축 TSV 중간 저장과 Impala ETL 테이블 관리 단계를 제거**했습니다.

### 2. 배치 규모와 기존 메모리 자원에 맞춰 DuckDB 선택

**[Issue]** 도입 검토 당시 시간별 압축 파일은 서버당 최대 약 800MB였습니다. 로그 서버 3대의 배치 규모와 기존 자원을 고려해 Apache Spark 분산 환경을 추가할 필요성은 낮다고 판단했습니다.

**[Solution]** 기존 서버의 **500GB RAM을 활용하는 DuckDB**를 선택해 서버별 입력을 3개 ETL 작업으로 병렬 처리했습니다. 파일당 800MB~1GB 처리 시 서버 전체 메모리 피크는 **30~39%**였습니다. 변환은 SQL·규칙 파일로 관리하고, 스키마 불일치는 실패 처리했습니다. 같은 Docker 이미지에 날짜·시간·서버를 전달해 정기 배치와 재처리를 통일했습니다.

### 3. Python 행 단위 호출을 줄이는 변환 방식 선택

**[Issue]** 로그마다 Python 함수를 호출하면 DuckDB 내부 처리와 Python 사이의 호출 비용이 누적됩니다. 같은 IP가 반복되는 로그에서도 매번 GeoIP를 조회할 필요는 없었습니다.

**[Solution]** 이벤트 분류, 불리언 변환, 공백 정규화는 SQL의 `CASE`와 정규식 함수로 처리했습니다. GeoIP는 **고유 IP 목록을 먼저 추출해 국가 매핑 테이블을 만들고 원본과 조인**하도록 구현했습니다. 조회 호출 수를 전체 로그 행 수에서 고유 IP 수로 줄이는 구조이며, 실행 로그에 고유 IP 수와 매핑 생성 시간을 남겨 병목을 확인할 수 있게 했습니다.

### 4. GeoIP 최신성 관리와 변환 오류 추적

**[Issue]** 기존 운영에서는 MMDB 갱신이 지연되고 국가 필드의 빈 값이 발생했습니다. 또한 숫자 표현 차이와 잘못된 값도 구분해야 했습니다.

**[Solution]** MMDB를 매 실행 시 갱신하고, 실패하면 로컬 DB를 사용하며 둘 다 없으면 국가를 `XX`로 기록했습니다. 숫자 변환 실패는 NULL·DLQ로 남기고, Audit 로그에 처리 상태·행 수·소요 시간·DLQ 건수를 기록했습니다.

### 5. 처리 대상 파티션을 기준으로 재처리와 후속 적재 연결

**[Issue]** KST 기준 1시간 입력 파일에 여러 미국 태평양 시간 기준 날짜의 이벤트가 포함될 수 있었습니다. Airflow가 배치 시각으로 단일 이벤트 날짜를 추정하면 일부 출력이 후속 적재에서 빠질 수 있었고, 날짜 전체를 재처리하면 인접 배치나 다른 서버의 데이터까지 영향을 받을 수 있었습니다.

**[Solution]** 분석 기준인 **이벤트 날짜(`logdate`)**와 재처리 기준인 **KST 입력 배치(`inputdatetime`)**를 분리했습니다. 이벤트 시간은 `America/Los_Angeles`로 변환해 서머타임을 반영하고, 파일명에 서버 ID를 포함해 재처리 범위를 구분했습니다.

새 Parquet 저장 후에는 **같은 배치·서버의 이전 파일만 정리**하고, 0행이면 기존 데이터를 유지합니다. 전체 배치를 원자적으로 교체하는 구조는 아닙니다. ETL은 실제 저장한 `(logdate, inputdatetime)`을 Airflow 이벤트로 전달해, 다운스트림이 모든 출력 파티션을 적재 대상으로 식별하도록 했습니다. 업로드 실패 시 성공 목록은 반환하지 않습니다.

## 4. Impact & Result

### 국가 미식별률: 1.8512% → 0.0008%

개선 전 **2026년 1월 1~10일**과 개선 후 **2026년 8월 1~10일**의 운영 데이터를 비교했습니다. 두 구간 모두 하루 평균 1억 건 이상을 처리했으며, 빈 문자열·NULL·`XX`를 미식별로 집계했습니다.

| 지표 | 개선 전 · 1월 1~10일 | 개선 후 · 8월 1~10일 |
|---|---:|---:|
| 전체 로그 | 1,106,875,397건 | 1,144,999,504건 |
| 국가 필드 빈 문자열 | 20,490,687건 | 0건 |
| 국가 필드 NULL | 0건 | 0건 |
| 국가 필드 `XX` | 0건 | 9,201건 |
| 미식별 합계 · 빈 문자열 + NULL + `XX` | 20,490,687건 | 9,201건 |
| 전체 건수 기준 미식별률 | **1.8512%** | **0.0008%** |

미식별률은 건수 기준으로 **약 99.96% 감소(1.8504%p)**했으며, 개선 후에도 `XX` 9,201건이 남았습니다.

### 기존 500GB 서버에서 시간 단위 로그 3개 병렬 처리

파일당 약 **800MB~1GB gzip 로그 3개를 병렬 처리**하는 동안 서버 전체 메모리를 관찰했습니다.

| 지표 | 운영 관측값 |
|---|---:|
| 서버 전체 RAM | 500GB |
| 평상시 사용량 | 약 23~24% · 115~120GB |
| ETL 실행 시 피크 사용량 | 약 30~39% · 150~195GB |
| 실행 전후 관측 증가량 | 약 35~75GB · 전체 RAM의 7~15%p |

**3개 병렬 실행 시 서버 사용률은 최대 약 39%였습니다. 수치는 다른 프로세스·캐시를 포함한 서버 전체 관측값이며, Spark 비교나 컨테이너별 측정값은 아닙니다.

### 저장·운영 구조 단순화

- HDFS의 TSV 기반 Impala ETL 테이블을 제거하고, gzip 원본과 분석용 Parquet만 보관했습니다.
- 정기 배치·재처리에 같은 Docker 이미지와 SQL을 사용하고, 실제 출력 파티션으로 후속 적재 범위를 정했습니다.

저장 용량·전송량 절감률과 처리 시간 개선율은 별도 비교 측정하지 않았습니다. 이 프로젝트에서는 **배치 규모와 가용 자원에 맞는 실행 엔진을 선택하고, 저장 구조와 재처리 기준을 함께 설계**한 점에 중점을 두었습니다.
