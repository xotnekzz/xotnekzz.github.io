# 경영진 KPI 대시보드 에이전트 프레임워크

## 1. 결론

이 프레임워크는 **증거 수집 에이전트 + 구조화된 Dashboard Bundle + 공유 Artifact를 복제한 결정론적 단일 HTML 렌더러 + 승인 경계가 있는 게시기**로 구성한다. LLM은 질의를 계획하고 근거를 해석하지만, HTML·상태·수치·관계 경로·시각 디자인을 임의로 만들지 않는다. 모든 화면 요소는 검증된 JSON 계약에서 렌더링하며 디자인은 아래 골든 레퍼런스에 고정한다.

### 골든 디자인 레퍼런스

- 원본: `https://claude.ai/code/artifact/94bfc064-369e-49b9-a32e-d3f3227dc51b`
- 로컬 골든 원본: `references/golden/ontology-kpi-dashboard.html`
- SHA-256: `c949cdb2058b14cb19ee8f8a3a1cefd8fe3c019c7f6c3dcff2ce85f19dba56bb`
- 식별자: `claude-artifact-94bfc064@1`
- 조사일: 2026-09-10
- 조사 화면: 경영진 KPI 보드, KPI 온톨로지 리포트, AI 추론 상세
- 계약 파일: `contracts/design-reference.json`

여기서 “같은 디자인”은 분위기가 비슷한 새 디자인이 아니라, 원본의 토큰·폭·간격·타이포그래피·컴포넌트 구조·반응형 분기·라우팅 동작을 보존한다는 뜻이다. 데이터와 문구 길이 때문에 생기는 자연스러운 높이 변화만 허용한다. 런타임과 테스트는 외부 URL보다 로컬 골든 원본을 우선하며, 원본 해시가 계약과 다르면 렌더링을 중단한다.

핵심 설계 원칙은 다음과 같다.

1. **숫자는 DB에서만** 가져온다. 온톨로지 설명문이나 모델 기억에서 수치를 복사하지 않는다.
2. **의미와 경로는 OpenMetadata에서** 확인한다. FQN, 관계명, 상태, 자산 ID를 추측하지 않는다.
3. **주장과 사실을 분리**한다. Observation, Hypothesis, Evidence, Decision, Outcome을 한 필드에 섞지 않는다.
4. **LLM 출력은 JSON까지**다. 최종 HTML은 버전이 고정된 렌더러가 만들고 요청별 로컬 실행 폴더에 저장한다.
5. **샘플/실데이터를 명확히 구분**한다. 일부라도 실데이터 검증이 실패하면 해당 KPI에 `sample` 또는 `unavailable` 표식을 붙인다.
6. **읽기와 쓰기를 분리**한다. 현재 전달 방식은 로컬 저장으로 고정하고, 향후 공개 게시·알림·온톨로지 후보 등록은 각각 별도 승인 경계를 가진다.
7. **디자인은 생성하지 않고 인스턴스화**한다. 오케스트레이터가 색, 카드 모양, 정보 배치, 폰트 크기를 선택하지 못하게 한다.
8. **기본 운영 프로필을 재사용**한다. 6개 타이틀, GitLab CAPD 열린 이슈 전체, 90일 관측, 7일 예측을 다음 생성의 기본값으로 삼고 요청이 있을 때만 변경한다.

## 2. 전체 구조

```text
Executive request
       │
       ▼
Request Interpreter ──► DashboardRequest
       │
       ▼
Evidence Orchestrator
  ├─ Ontology adapter ───── OpenMetadata REST / Jena SPARQL
  ├─ Metric adapter ─────── query-db → Doris read-only
  ├─ Pipeline adapter ───── Airflow API/MCP
  ├─ BI adapter ─────────── Metabase API / Superset API
  ├─ Quality adapter ────── OpenMetadata testCase/testSuite
  └─ Decision adapter ───── GitLab candidate issues / approved cases
       │
       ▼
Evidence Normalizer ──► EvidenceBundle
       │
       ▼
Inference & Recommendation Engine
       │
       ▼
Policy / Quality Gates ──► DashboardBundle
       │
       ▼
Golden-reference Renderer ──► index.html + visual manifest
       │
       ▼
Local Artifact Writer ──► versioned dashboard.html
```

`openmetadata-ontology-search`와 `query-db`는 현재 MCP 서버라기보다 **로컬 skill adapter**다. 오케스트레이터에서는 MCP와 동일한 포트 인터페이스로 감싸되, 기존 안전 규칙을 그대로 유지한다. 나중에 원격 다중 클라이언트가 필요할 때만 TypeScript 기반 Streamable HTTP MCP로 승격한다.

### 디자인 수집 및 재현 도구

원본 페이지 조사는 Browser/CUA의 DOM snapshot, computed style, 화면별 screenshot을 사용했다. 다운로드된 원본 코드는 `references/golden/ontology-kpi-dashboard.html`에 바이트 단위로 동일하게 보관한다. 런타임 대시보드 생성 때마다 외부 페이지를 다시 읽지 않고 이 파일을 사용한다. 원본을 변경해야 할 때는 기존 파일을 덮어쓰지 않고 새 reference id와 hash를 만든다.

렌더러는 다음 요소를 그대로 보존한다.

- sticky topbar, 좌측 브랜드와 우측 범위/select·샘플 배지·기준일
- `max-width: 1220px`, 본문 좌우 24px, 상단 24px, 하단 72px
- KPI grid `repeat(auto-fit, minmax(272px, 1fr))`, gap 12px
- tile/panel radius 6px, 1px border, 상태 stripe 3px
- overview의 반응형 KPI 타일 그리드와 하단 `1fr + 340px` 이상징후/액션 구조. 기본 운영 프로필은 동일 타일 패턴으로 9개 KPI를 배치한다.
- KPI detail의 hero, 추이/driver 2열, 관계/segment 2열, evidence table
- reasoning의 150px 단계 메타 + 본문 구조, lifecycle segmented stepper
- 900px 이하 2열→1열, 760px 이하 reasoning step→1열
- hover lift 1px, focus ring 2px, reduced-motion 대응

KPI 상세에는 승인된 확장 `kpi-detail-multi-window@1`을 적용한다. 메인 타일은 대표 윈도우 하나를 유지하고, 상세 hero 하단의 segmented strip에서 Retention `D1/D3/D7/D14/D28`, ROAS `D0/D1/D3/D7/D14/D28`을 전환한다. 선택 시 값·term FQN·임계 정보·추이/예측·driver·segment가 함께 바뀐다. 다른 KPI는 윈도우가 정의된 경우에만 이 strip을 표시한다.

모든 KPI 상세에는 `kpi-detail-data-period@1`을 적용한다. hero 안의 compact band에서 관측 기간, 예측 기간, 시간대를 표시하고 기간형 KPI에는 선택 윈도우 기준 최신 완결 코호트를 추가한다. 상단 고정 바에는 관측/예측 기간을 축약 표시한다.

### 승인된 기본 운영 프로필 (`capd-open-issues-20260910@1`)

- 타이틀: Word Cookies, Bubble Pop, Bubble Pop Origin, Jewels Magic, Brick Out, StoneAge Merge
- 메인 KPI: GitLab `regular/manager/cxo/capd`의 열린 이슈 전체를 한 항목씩 표시한다. 2026-09-10 스냅샷은 21개이며 `contracts/executive-kpi-registry.json`에 고정했다.
- 재무 정의: `매입`은 OpenMetadata `02_01_GameMetrics.Finance.ad_spend` 정의에 따라 손익상 UA 광고비로 해석한다.
- 파생 정의: IAP 매출 비중은 `inapp_revenue / revenue`, ARPU는 `revenue / DAU`다. 승인된 독립 glossary term이 없으면 파생지표·KnowledgeGap으로 표시한다.
- 기간: 일반 KPI는 최근 90일, 기간형 KPI는 각 윈도우의 최신 완결 코호트까지 조회한다.
- 예측: `tools/kpi_linear_forecast.py`로 최근 56일 OLS 학습 후 7일을 예측하며 95% 예측구간을 함께 표시한다.
- 이상징후: 최신 관측값의 OLS 잔차 z-score 절댓값이 2 이상이면 검토 대상으로 올린다.
- driver: 표준화 회귀계수의 절댓값을 R² 범위에서 설명 비중으로 배분하고 `1−R²`를 회색 `설명되지 않음(잔차)`으로 표시한다. 인과 기여도로 부르지 않는다.
- 데이터 공백: 타이틀·KPI 조합의 관측값이 없으면 0으로 채우지 않고 `unavailable`과 점검 항목을 표시한다.

### GitLab 기반 경영진 KPI 카탈로그

경영진 KPI의 시스템 오브 레코드는 GitLab `regular/manager/cxo/capd`의 열린 이슈다. 실행할 때마다 열린 이슈를 조회하고 `contracts/executive-kpi-registry.json`과 대조한다. 열린 이슈 하나를 대시보드 항목 하나로 보존하며, 닫힌 이슈는 기본 화면에서 제외한다. 신규·제목 변경·종료를 발견하면 registry drift와 KnowledgeGap으로 기록한다.

이슈가 시장 인사이트, Benchmark, CX처럼 단일 수치가 아닌 경우에도 항목 자체를 누락하지 않는다. 대신 `context` 또는 `composite` 건강 신호로 분류하고 승인된 산식과 자산이 생길 때까지 `unavailable`로 표시한다. 숫자를 임의로 대입해서는 안 된다. Revenue 이슈의 대표 지표는 순매출 `net_revenue`이며 IAP·IAA 매출은 각자의 이슈와 KPI로 유지한다.

### 경영진 건강상태 요약과 쉬운 driver 설명

overview 상단에는 정상·주의·위험·데이터 공백 개수, 가장 중요한 변화, 즉시 확인할 항목을 2~4문장으로 요약한다. KPI 상세 hero에는 현재값, 비교 변화, 예측, 품질 상태, 가장 큰 설명 변수 또는 잔차를 1~3문장으로 연결한다. 두 요약 모두 Observation과 Hypothesis를 구분하고 인과를 단정하지 않는다.

화면에서는 `드라이버 기여도` 대신 `무엇이 변화를 설명하나`를 사용한다. 각 막대는 최근 관측기간에 KPI와 함께 움직인 정도를 모델이 나누어 보여주는 것이며 원인 비율이 아니다. `unexplained`는 `데이터에 아직 담기지 않은 영향`으로 표시한다. β와 R²는 상세 보조 문구에만 남기고, 캠페인·버전·LiveOps·국가·플랫폼 데이터 보강 필요성을 함께 알려준다.

드라이버 후보는 임의의 회귀 입력값이 아니다. 매 실행 OpenMetadata에서 KPI term의 `hasDriver`, `influencedBy`, `mayImpact` 관계를 조회하고, 관계 방향과 시간 선행 조건을 통과한 경우에만 계산한다. 예를 들어 `RetentionRate —hasDriver→ AcquisitionQuality`는 확인됐지만, D28 리텐션은 설치 후 28일 결과이므로 설치 수의 driver로 사용할 수 없다. `possibleCauseOf`는 Candidate 가설로 표시할 수만 있고 회귀 후보로 자동 승격하지 않는다. 직접 측정 자산이 없으면 비율을 만들지 않고 측정 연결 공백을 노출한다. 조회 snapshot과 선택 규칙은 `contracts/ontology-driver-policy.json`에 남긴다.

모든 CAPD KPI는 `contracts/ontology-kpi-graph.json`의 OpenMetadata snapshot을 가진다. 이 파일은 KPI ID별 승인 term FQN, 직접 `relatedTerms`, 관계 유형과 KnowledgeGap을 보관한다. 화면의 온톨로지 관계 패널은 이 snapshot을 그대로 렌더링한다. 용어가 없는 KPI는 GitLab 이슈명을 FQN처럼 대체하지 않으며, `승인 용어 없음`으로 표시한다.

승인 term이 있는 KPI는 allowlist 관계만 따라 루트에서 **BFS depth 3**까지 탐색한다. snapshot은 각 노드의 FQN·표시명·OpenMetadata glossary UI href(`https://openmetadata.datawave.co.kr/glossary/{FQN}`)·깊이와 edge 관계명을 저장한다. 상세 화면은 직접 관계 칩과 이 전체 경로 그래프를 함께 보여주며, 모든 term/노드는 실제 glossary UI 주소로 연결한다. 그래프의 가로·세로 스크롤은 카드 내부에서만 허용한다.

경영진 첫 화면은 수익화, 사용자·장기 코호트, 즉시 확인·데이터 공백이라는 세 신호를 같이 보여준다. 상세 화면은 관측 동행 지표와 검증할 온톨로지 드라이버를 분리하며, 시간 정렬된 측정 계약이 없으면 비율과 인과 추론 대신 `추론 보류` 및 필요한 계약을 표시한다. 기간형 코호트 KPI는 최신 완결 설치 코호트 날짜와 지연 해석 주의를 명시한다. 관계 카드는 직접 의사결정 경로를 기본으로, 전체 depth-3 BFS를 펼치기로 제공한다.

메인에는 순매출을 기본 대상으로 한 `핵심 인사이트 · Candidate`를 추가한다. 이 인사이트는 `관측 신호`, `트래픽 또는 반대 신호`, `다음 검증`, `신뢰 수준`을 한 화면에서 제시한다. 모든 수치는 driver explanation의 share, R², unexplained residual에서 계산하며, “원인”이나 “견인”이 아니라 “강하게 함께 움직인 관측 신호”라고 표현한다. 동일한 포맷을 KPI 상세에도 적용한다.

### SQL 계획 캐시

재사용 가능한 읽기 전용 SQL은 `queries/cache/{queryId}.sql`에 저장한다. `queries/manifest.json`은 KPI, source FQN, grain, required columns, parameter contract, schema fingerprint, query hash를 기록한다. `tools/query_cache.py`는 템플릿 해시와 입력값을 검증한 뒤 실행할 SQL을 stdout으로 출력한다.

캐시는 SQL 계획만 저장하며 결과·자격증명은 저장하지 않는다. manifest 계약과 스키마 fingerprint가 일치할 때만 재사용하고, SQL은 사용자에게 먼저 보여준 뒤 query-db를 통해 매번 최신 데이터를 조회한다. 계약이 달라지면 기존 파일을 조용히 덮어쓰지 않고 새 query version을 만든다.

정확한 색·글꼴·크기는 `contracts/design-reference.json`을 단일 출처로 사용한다.

OpenMetadata와 DB를 하나의 거대한 MCP로 합치지 않는다. 인증·권한·장애 범위가 다르며, DB read-only 계약과 OpenMetadata 승인 기반 write 계약이 흐려지기 때문이다.

## 5. 표준 데이터 계약

### DashboardRequest

`contracts/dashboard-request.schema.json`이 자연어 요청을 실행 가능한 명세로 고정한다.

- `scope`: 전체 포트폴리오 또는 최대 6개 타이틀 목록
- `asOf`, `timezone`, `lookbackDays`, `forecastDays` — 기본값은 각각 KST 직전 완료일, `Asia/Seoul`, 90일, 7일
- `kpis`: term FQN 또는 자연어 KPI 후보
- `dataMode`: `live`, `sample`, `live-with-fallback`
- `publish`: 현재 계약에서는 `none`으로 고정. 호스팅 기능을 도입할 때 별도 schema version에서 확장
- `localOutputRoot`: 기본 `artifacts/runs`
- `templateVersion`: 재현 가능한 UI 버전
- `designReference`: 반드시 `claude-artifact-94bfc064@1`

### DashboardBundle

`contracts/dashboard-bundle.schema.json`은 렌더러의 유일한 입력이다. 중요한 필드는 다음과 같다.

- `provenance`: source type, entity FQN, query hash, observedAt, freshness
- `kpis[]`: value, delta, threshold, status, series, forecast, segments, drivers
- 기간형 KPI는 `metricFamily`, `defaultWindow`, `windows[]`를 추가하고 각 window가 별도 term FQN과 상태를 가진다.
- 모든 KPI는 `measurementPeriod`에 관측 시작/종료, 예측 시작/종료, 시간대, 완결 지연 일수를 제공한다.
- `anomalies[]`: 판단 문장과 실제 그래프 경로
- `recommendations[]`: 항상 기본 `Candidate`
- `decisionCases[]`: 단계별 클래스, 신뢰도, 직접/간접 근거
- `quality`: coverage, freshness, test results, unresolved gaps

원시 SQL 결과나 HTML 문자열은 번들에 넣지 않는다. 텍스트는 escape하고, 렌더러는 허용된 필드만 DOM에 배치한다.

## 6. 실행 상태 머신

```text
RECEIVED
  → RESOLVING_ONTOLOGY
  → PLANNING_QUERIES
  → COLLECTING_EVIDENCE
  → NORMALIZING
  → INFERRING
  → VALIDATING
  → RENDERING
  → QA_PASSED
  → LOCAL_READY
```

부분 실패는 `DEGRADED_READY`로 수렴할 수 있다. 단, 다음은 로컬 완료본으로 승격할 수 없다.

- 요청된 6개 KPI 중 식별되지 않은 KPI가 있는데 샘플 표시도 없음
- 수치의 DB provenance 또는 `asOf`가 없음
- 존재하지 않는 FQN/관계가 포함됨
- Candidate 가설을 `confirmedCauseOf`로 표현함
- 직접 근거가 없는데 신뢰도가 0.6을 초과함
- 본문 가로 스크롤, 라우팅 오류, 테마 토큰 누락
- 원본과 비교한 DOM 구조 fingerprint 또는 visual regression 임계 초과
- 골든 원본 SHA-256이 `DesignReference` 계약과 불일치

실행 순서는 [런타임 시퀀스 다이어그램](runtime-sequence.svg)에 정리했다.

## 7. 한 번의 요청이 처리되는 방식

1. 요청을 `DashboardRequest`로 정규화한다. 누락된 날짜는 한국 시간 기준 직전 완료일, 관측 90일, 예측 7일, 데이터 모드는 `live-with-fallback`, 게시는 `none`, 로컬 저장 루트는 `artifacts/runs`를 기본값으로 둔다.
2. KPI 후보별로 OpenMetadata hybrid search를 수행하고, 관련 관계만 allowlist한 BFS를 깊이 3으로 실행한다.
3. `measuredBy`/`representedBy` 경로에서 실제 table/column FQN을 `get`으로 확인한다. 확인되지 않은 자산은 쿼리 계획에서 제외한다.
4. Metric, Airflow, quality, BI, decision evidence 수집은 서로 독립적인 부분만 병렬 실행한다.
5. 시점·게임 ID·단위·집계 grain을 정규화한다. 총계와 타이틀별 값의 reconciliation을 검사한다.
6. 정규화된 시계열을 `tools/kpi_linear_forecast.py`에 전달해 56일 OLS 기반 7일 예측, 95% 예측구간, 잔차 z-score와 표준화 회귀 driver 설명 비중을 계산한다.
7. 이상과 가설을 생성하되 `possibleCauseOf`, `supportedBy`, `refutedBy`, `confirmedCauseOf`를 구분한다. 경합 가설은 낮은 신뢰도로 유지한다.
8. `DashboardBundle`을 스키마와 정책 규칙으로 검사한다. 잔차 driver, 예측구간, 직접/간접 근거 표시 여부도 검사한다.
9. 골든 레퍼런스 템플릿이 단일 HTML을 생성한다. JS는 라우팅, scope 전환, SVG 차트, 테마, tooltip만 담당하며 외부 런타임 라이브러리를 사용하지 않는다. 차트 x축과 tooltip에는 상대 일수 대신 실제 날짜(`YYYY-MM-DD`)를 표시한다.
10. `overview`, `kpi`, `reasoning`을 고정 viewport에서 캡처하고 원본 baseline과 비교한다. DOM landmark, bounding box, token fingerprint를 먼저 검사하고 screenshot diff를 보조 게이트로 쓴다.
11. 정적 HTML을 `artifacts/runs/{runId}/dashboard.html`에 원자적으로 저장하고 manifest를 함께 기록한다. 검증을 통과한 최신본에는 `artifacts/latest.html`로 접근할 수 있게 한다.
12. 현재는 로컬 절대 경로를 반환하고 종료한다. 사용자가 별도로 호스팅을 요청한 경우에만 publish adapter를 호출한다.
13. 분석 중 재사용 가치가 있는 사례가 발견돼도 자동 등록하지 않는다. 기존 OM 사례와 GitLab 후보를 먼저 검색하고, 사용자에게 초안을 보여준 뒤 승인된 경우에만 후보 이슈를 만든다.

## 8. 추론 규칙

```text
Observation  = DB에서 관측되고 provenance가 있는 값
Hypothesis   = possibleCauseOf로 연결된 설명 후보
Evidence     = 자산, 테스트, 대시보드, 파이프라인, 승인 문서
Decision     = 사람 또는 승인 워크플로가 선택한 것
Outcome      = 실행 후 별도 기간에 관측된 결과
```

- `relatedTo`만 있는 연결은 간접 근거다.
- `supportedBy`는 지지이지 인과 확정이 아니다.
- `confirmedCauseOf`는 승인된 기존 관계를 읽어 표시할 수만 있다. 생성 플로우에서는 인간 승인 전 절대 만들지 않는다.
- 그래프 경로가 없으면 신뢰도 상한은 0.6이다.
- 최신 testSuite가 실패했거나 pipeline freshness SLA를 넘으면 수치가 존재해도 상태를 최소 `주의`로 올린다.
- driver 합계가 100%가 되지 않도록 모델이 억지 보정하지 않는다. 차이를 `설명되지 않음(잔차)`으로 표시한다.
- driver 막대는 표준화 회귀의 설명 비중이며 `influencedBy`나 `confirmedCauseOf`를 통계 결과만으로 생성하지 않는다.
- 설명력을 높이려면 캠페인 믹스, 앱 버전, LiveOps 이벤트, 국가·플랫폼 구성비를 우선 feature로 추가한다.
- 예측은 모델명, 학습/기준 기간, 생성 시각, 구간 수준을 provenance에 남긴다. 예측기를 연결하지 않았다면 샘플로 명시한다.

## 10. 산출물과 버전 전략

한 번의 실행은 다음 묶음을 로컬에 만든다. `runId`는 `{KST timestamp}-{scope slug}-{request hash 8자}` 형식을 사용해 충돌을 피한다.

```text
artifacts/
├── latest.html           # 마지막으로 검증을 통과한 대시보드의 편의용 복사본
└── runs/{runId}/
    ├── request.json      # 정규화된 요청
    ├── evidence.json     # source provenance와 원시 정규화 결과
    ├── dashboard.json    # 렌더러 입력
    ├── validation.json   # gate 결과와 경고
    ├── dashboard.html    # 단일 파일 대시보드
    └── manifest.json     # hash, template version, timestamps, local path
```

재현성 키는 `sha256(normalizedRequest + sourceWatermarks + templateVersion)`로 계산한다. 동일 키가 이미 성공한 경우 기존 로컬 HTML을 반환할 수 있다. `latest.html`은 임시 파일에 완전히 쓴 뒤 rename하는 방식으로 교체해 중간 상태가 노출되지 않게 한다. 과거 `runs/{runId}` 폴더는 덮어쓰지 않는다.

## 12. 구현 단계

### Phase 1 — 재현 가능한 로컬 생성기

- 두 기존 skill을 adapter로 감싼다.
- 두 JSON Schema와 고정 HTML template을 구현한다.
- 공유 Artifact를 골든 baseline으로 캡처하고 `DesignReference` 기반 renderer를 구현한다.
- 샘플 fixture로 3단 라우팅/차트/테마를 회귀 테스트한다.
- 실제 KPI 1개를 end-to-end로 연결한다.

### Phase 2 — 운영 근거 확장

- Airflow freshness, OpenMetadata testCase, Metabase/Superset provenance를 추가한다.
- GitLab CAPD 열린 이슈 전체와 타이틀 6종을 지원한다.
- 부분 실패와 stale 상태를 화면에 표현한다.

### Phase 3 — 로컬 산출물과 감사

- 실행별 immutable 로컬 폴더와 `latest.html` 원자적 갱신을 연결한다.
- 호스팅은 기본 실행에서 제외하고 별도 기능 플래그로 남긴다.
- GitLab에 renderer 변경과 DecisionCase 후보 이력을 남긴다.

### Phase 4 — 평가와 운영화

- 서로 독립적이고 검증 가능한 read-only 평가 질문 10개를 만든다.
- Recall@5, 관계 경로 완전성, SQL 정확성, 수치 reconciliation, p95 latency를 측정한다.
- shadow run 이후 수동 검토율과 오류 유형을 기준으로 자동 게시 범위를 넓힌다.

## 13. 권장 첫 수직 슬라이스

현재 기준 수직 슬라이스는 `전체 포트폴리오 + 6개 타이틀 + GitLab CAPD 열린 이슈 전체 + 최근 90일/예측 7일 + 로컬 dashboard.html`이다. term FQN 확인, `measuredBy` 자산 검증, Doris 수치, 모델 provenance, 잔차 driver, 데이터 공백 표시, 추론 신뢰도 상한, 단일 HTML 저장을 한 실행에서 함께 검증한다.
