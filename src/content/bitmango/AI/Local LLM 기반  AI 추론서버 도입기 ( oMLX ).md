
## 배경

Gemini API 비용이 인상됨에 따라 새로운 대안이 필요해졌습니다.

Pro, Max(ultra) 등 구독 옵션을 선택해서 쓰는 것이 API를 사용하는 것 보다 비용이 20배 이상 효율적이라 하여 대체하려고 검토를 해보았으나, google generative ai 등 SDK 형태로 서비스하고 있는 방식은 플랜구독형인 OAuth2로 인증이 불가능합니다.

OpenRouter를 사용하여 가성비 모델(Deepseek-v4-flash)을 사용하는 방법이 최고의 대안이긴하나
사내 보유중인 맥스튜디오(M2 Ultra 192GB)로 로컬 LLM 테스트를 해보면 좋을 것 같다는 생각이 들었습니다.

사내에서 Gitlab 코드 리뷰, Gitlab 자동 Release 생성, WatchDog(이메일 분류) 등 Gemini API 사용하여 AI를 활용한 업무 도구가 있는데 Local LLM만으로 충분히 가능할 것으로 보여 대체해보고자 합니다. 

## Model 선택

최근의 어떤 오픈 모델이 가장 괜찮은지 서치해본 결과

`Qwen3.6-35b-a3b` 모델이 맥스튜디오에서 쾌적하게 돌릴 수 있을 것이라고 판단했습니다.

MoE(Mixture of Expert) 아키텍처를 사용하며 35b (350억개)파라미터로 학습된 모델을 3b(30d억개)
파라미터만 활성화하여 작동하기 때문에 메모리를 많이 점유하지 않고 빠른 토큰속도를 지원합니다.

##### MoE 아키텍처란

하나의 거대한 인공지능 모델을 여러 개의 작은 '전문가(Expert)' 네트워크로 나누고, 입력된 데이터나 질문에 따라 가장 적합한 전문가만 선택적으로 활성화하여 처리하는 아키텍처


모델명에  `Qwen3.6-35b-a3b-4bit` 또는 `Qwen3.6-35b-a3b-8bit`  bit가 뒤에 붙는데 이는 양자화 모델입니다.
양자화 모델은 16bit,32bit 단위로 숫자를 연산하여 막대한 메모리(VRAM)이 필요한데 이를 8bit 또는 4bit로 압축(양자화)하여 모델의 크기와 요구 메모리를 줄이는 기술 입니다.

8bit - 원본 모델 대비 성능저하가 거의 없이 메모리 요구량을 절반 수준으로 줄여줍니다.
4bit -  미세한 답변이 질이 떨어질 수 있으나 메모리 사용량을 1/4 수준으로 낮춰줍니다.

`Qwen3.6-35b-a3b` 모델 기준 8bit를 사용시 메모리를 약40gb정도, 4bit 사용시  20gb 정도 메모리를 점유합니다.

192GB라는 넉넉한 메모리를 가지고 있기 때문에

`Qwen3.6-35b-a3b-8bit` 모델을 최종으로 선택하였습니다.

https://qwen.ai/blog?id=qwen3.6-35b-a3b

## LM Studio vs Ollama

Local LLM을 구동하기 위해서는 LM Studio, Ollama 를 범용적으로 많이 사용합니다.

LM Studio는 GUI를 통해 Local LLM을 실행할 수 있는 데스크톱 애플리케이션입니다. 모델 검색, 모델 전환, 채팅 기능 등 사용자 편의성에 중점을 두었으면, 필요에 따라 다른 도구에서 호출 할 수 있도록 로컬 서버를 실행할 수 있습니다.

Ollama는 명령줄 워크플로우와 로컬 HTTP API를 통해 LLM을 로컬에 다운로드하고 실행할 수 있도록 도와주는 도구입니다.

`Qwen3.6-35b-a3b-8bit`  모델로 둘 다 사용해 본 결과 Ollama보다 LM Studio가 모델 검색, 서버 구동 등  편리한 GUI를 제공하며,  로컬 서버의 응답속도가 더 빨랐습니다. 

## llama.cpp vs MLX

로컬 LLM을 구동하기 위해서는 런타임을 설정해야합니다.

처음에는 범용적으로 많이 사용되는 llama.cpp기반의 gguf 모델을 사용하였는데 Apple Silicon을 위한 MLX 프레임워크가 있다는것을 알게 되었습니다.

서로 비교해보고 우리 장비에 어떤게 맞을지 결정하고자 합니다.
##### llama.cpp
메타의 llama 모델을 일반 사용자의 컴퓨터에서 돌아가게끔 만들어진 오픈소스 프로젝트입니다.
모든 플랫폼(mac, windows, linux, android 등)에서 사용가능하며, 다양한 하드웨어에서의 가볍고 빠른 추론 및 서빙이 가능합니다. GGUF 포맷을 지원합니다.
##### MLX
Apple의 AI 연구팀이 직접 만든 머신러닝 프레임워크입니다. Apple 생태계의 특화된 파이토치(PyTorch)입니다.

Apple Silicon칩에는 CPU, GPU, AI연산을 위한 NPU가 하나로 합쳐진 통합메모리 구조입니다. MLX는 이 구조를 완벽하게 이해하고 만들어졌기 때문에 AI를 돌릴때 메모리를 복사하지 않고(Zero Copy) 낭비없이 빠른속도와 높은 전력효율을 보여줍니다.

## oMLX로 변경

LM Studio에서 MLX 모델로 서버를 배포하면 동시성을 1로 제한되는 한계가 있었습니다.

따라서 모델이 리즈닝 무한반복으로 인해 대답을 못하고 있으면 이후에 들어오는 요청에대해 큐가 계속 쌓이게 됩니다. 따라서 대책이 필요하여 MLX 기반으로 서빙을 잘할 수 있는 프레임워크를 찾았습니다.

바로 oMLX입니다.

##### oMLX란
Apple Silicon 기반 Mac환경에서 LLM을 가장 빠르고 효율적으로 실행할 수 있도록 설계된 로컬 AI 추론 서버 플랫폼입니다.

MLX를 기반으로 개발자나 일반 사용자가 실제 서비스 운영 환경(서버)처럼 편리하게 쓸 수 있도록 운영 체계와 사용자 인터페이스를 덧붙인 제품입니다.

##### 장점

- Two-Tier KV Cache
  oMLX는 컨텍스트가 길어지면 메모리(VRAM)부족으로 맥이 느려지거나 멈추는 병목현상이 있었는데 2단계 KV 캐시(Two-Tier KV Cache)기술을 사용합니다.

  자주 쓰는 데이터는 메모리(Hot Cache)에 두고, 당장 쓰지 않는 과거 대화 맥락은 SSD(Cold Cache)로 빼두는 방식입니다. 덕분에 램 용량이 적은 맥에서도 버벅이지 않고 모델을 돌릴 수 있습니다.

- Continuous Baching 
  답변이 끝난 요청은 즉시 내보내고 새 요청을 실시간으로 채워 넣어 맥북의 자원을 쉬지 않고 100% 효율적으로 가동합니다.
-
- PagedAttention 알고리즘
  메모리를 잘게 쪼개어 가상으로 관리함으로써 낭비를 없애고, 동시 처리가 많아져도 RAM이 가득 차는 파편화 문제를 해결합니다.

## 결론

Local Model이 예전보다 경량화되고 성능이 좋아진 것을 알게 되었고, 

애플 실리콘의 최적화된 MLX, 그걸 AI 추론서버로 서빙하는 oMLX와 같은 좋은 도구의 등장으로 Opus 4.7, Gemini 3.1 Pro, GPT 5.5 등 클라우드 모델의 수준까지는 아니지만 충분히 로컬 모델로도 에이전트를 활용할 가치가 있다고 느꼈습니다.
