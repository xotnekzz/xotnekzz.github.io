## Background & Challenges

공고가 설명하는 대상은 특정 분석 모델 하나가 아니라 **전사 데이터 활용을 위한 수집·적재·처리 파이프라인**이다. 거래소 도메인을 고려하면 주문·체결·입출금·정산 같은 거래 데이터와 고객 행동·외부 시세 등의 데이터가 후보 원천이다. 이는 면접에서 흐름을 설명하기 위한 예시일 뿐, 각 원천의 실제 수집 범위는 확인되지 않았다.

이 역할의 핵심 제약은 처리량만이 아니다. 주문과 체결, 입출금과 정산의 숫자는 집계 기준·이벤트 순서·정정 이력에 따라 달라질 수 있다. 따라서 **언제 들어왔는가(신선도)**, **빠진 것이 없는가(완전성)**, **두 번 반영되지 않았는가(멱등성)**, **업무 원장과 맞는가(정합성)**를 서로 다른 검증 항목으로 다뤄야 한다. 공고가 이 네 종류의 품질 이슈와 재처리를 직접 요구한다.

## Architecture: Data Flow & Verification Points

1. **Sources → 수집 계약.** 거래·주문·정산, 고객 행동, 외부 데이터는 서로 다른 변경 방식과 시각 기준을 가진다. 먼저 원천별 소유자, 기본키·이벤트 ID, 발생 시각, 수정·취소 의미, 허용 지연을 정의한다. 원천 DB의 로그 기반 CDC, 애플리케이션 이벤트, API·파일 배치 중 무엇을 쓰는지는 공고에 없다.
2. **Ingestion → 버퍼와 재시도.** 스트림 후보라면 Kafka·Kinesis·MSK, 배치 후보라면 추출 작업과 스케줄러가 변경을 전달한다. 이 제품들은 공고의 우대사항일 뿐 현재 운영 스택을 뜻하지 않는다. 수집 시점의 오프셋·커서·파일 식별자를 기록해야 실패 후 어디서 재개할지 결정할 수 있다. 스트림 발행 주기와 DW 반영 주기는 별도로 확인해야 한다.
3. **Raw landing → 재현 가능한 원본.** 수집 결과를 변경 전 의미를 잃지 않는 원본 영역에 보관하고, 원천 ID·이벤트 시각·수집 시각·스키마 버전을 붙이는 구성이 합리적이다. 재처리 때 중복 유입을 막기 위한 키와 원본 보존 기간은 실제 정책 확인 대상이다. Iceberg·Delta Lake·Hudi는 공고의 Lakehouse 경험 예시이며 채택 여부는 미확인이다.
4. **Processing → 정제·대사.** 배치 또는 스트림 처리에서 스키마 검증, 중복 제거, 지연 이벤트 처리, 취소·정정 반영을 수행한다. Spark·Flink는 공고상 경험 예시다. 주문·체결·정산 같은 도메인에서는 단순 행 개수보다 **원천과 분석계의 건수·금액·상태별 합계**를 같은 컷오프 시각으로 대사하는 설계가 중요하다. 대사 기준과 책임 주체는 면접에서 확인해야 한다.
5. **DW → 마트 → 소비.** 정제된 사실을 공통 지표 정의와 함께 DW에 적재하고 목적별 데이터 마트로 제공한다. Redshift·BigQuery·Databricks 역시 공고의 클라우드 플랫폼 경험 예시다. BI·운영 분석·위험 탐지 등의 소비 목적은 가능한 활용 예시이며 특정 내부 팀이나 테이블에 연결됐다고 단정할 수 없다.
6. **횡단 운영 계층.** 각 경계에서 원천 대비 수집량, 마지막 성공 시각, 처리 지연, 중복률, 실패 건수, 대사 차이를 계측한다. 알림은 소유자와 심각도를 포함하고, 재처리는 원본에서 대상 구간을 다시 읽어도 결과가 같도록 설계한다. 공고가 명시한 모니터링·알림·장애 대응·재처리 책임이 이 계층에 해당한다.

## 예상 기술 스택: 가장 그럴듯한 조합

**주 가설:** `운영 원천 → Python 기반 배치 ETL / 일부 스트림 수집 → S3 원본 영역(추정) → Airflow 오케스트레이션 → Redshift DW → SQL 데이터 마트·BI`. 두 공고를 함께 보면 **AWS + Airflow + Redshift + Python/SQL**이 면접 준비의 우선순위가 높다. 다만 이는 공고의 경험 요건을 연결한 추론이며, 실제 데이터 경로가 위 순서라는 뜻은 아니다. 스트림 영역은 현재 공고가 Kafka·Kinesis·MSK를 함께 열거해 특정 제품을 고르기 어렵다.

| 데이터 흐름 | 우선 예상 기술 | 확신 수준과 근거 |
|---|---|---|
| 실행 환경 | **AWS** | **상대적으로 높음.** 별도 빗썸 데이터 분석 엔지니어 공고가 AWS 환경을 구체적으로 언급한다. 이 팀과 같은 계정·플랫폼을 쓰는지는 미확인이다. |
| 배치 개발·오케스트레이션 | **Python, SQL, Airflow** | **상대적으로 높음.** 관련 공고가 Python 파이프라인과 Airflow를 함께 우대하고 SQL을 필요역량으로 명시한다. 현재 팀의 배치 도구인지 확인이 필요하다. |
| 분석 저장소 | **Redshift** | **상대적으로 높음.** 관련 공고가 Redshift 환경을 명시한다. 현재 공고는 Redshift·BigQuery·Databricks를 모두 경험 예시로 열거하므로 단일 DW로 확정할 수 없다. |
| 원본 보관·백필 | **S3** | **중간.** AWS 기반 배치와 재처리를 가정하면 자연스러운 원본 착지 후보이지만, 두 공고에 S3 제품명은 없다. |
| 이벤트 전달 | **Kafka 또는 MSK**, 대안 **Kinesis** | **중간 이하.** 현재 공고의 우대 기술이며 대용량 스트림 수집에 적합하다. Kafka와 MSK를 서로 다른 계층으로 중복 배치하기보다, MSK를 AWS 관리형 Kafka 선택지로 본다. 실제 사용 여부와 적용 도메인은 미확인이다. |
| 대용량 변환 | **Spark**, 실시간 상태 처리 시 **Flink** | **낮음~중간.** 둘 다 현재 공고의 우대 기술이다. 복잡한 스트림 집계가 필요한지 확인 전에는 Flink 도입을 예상 중심축으로 두기 어렵다. |
| Lakehouse 테이블 | **Iceberg / Delta Lake / Hudi 중 하나** | **낮음.** 우대사항은 포맷 경험을 폭넓게 제시한다. 셋을 모두 사용하거나 이미 도입했다고 해석할 근거는 없다. |
| 품질·메타데이터 | **자체 검증 로직 + 모니터링**, 제품은 미상 | **역할은 높음, 제품은 미확인.** 두 공고가 품질 개선을 요구하고 현재 공고가 알림·재처리를 명시하지만, 특정 관측성·카탈로그 제품은 제시하지 않는다. |

**면접용 한 문장:** “관련 공고를 보면 AWS에서 Python·Airflow로 배치 파이프라인을 운영하고 Redshift를 DW로 활용할 가능성을 먼저 생각했습니다. 현재 공고의 Kafka/MSK·Spark 우대사항은 대용량 또는 스트림 경로가 별도로 있거나 확장 중이라는 신호로 읽었습니다. 실제 운영 범위와 제품 선택은 어떻게 되어 있나요?”

## Solution & Technical Insights

### [Issue] 수집 성공인데 DW에는 일부 데이터가 없다

**[Solution]** 원천 추출, 버퍼 도착, 원본 착지, DW 반영의 체크포인트를 분리한다. 각 단계의 건수와 최대 이벤트 시각을 기록하면 어느 경계에서 누락·지연이 생겼는지 좁힐 수 있다. 재수집은 영향 구간과 원천 식별자를 지정하고, 완료 후 원천·DW 대사를 다시 수행한다. 이는 제안 설계이며 현재 장애 절차를 설명하는 것은 아니다.

### [Issue] 재시도와 늦게 도착한 이벤트가 중복 집계를 만든다

**[Solution]** 전달은 중복 가능성을 전제로 두고, 원천 이벤트 ID 또는 업무 키와 버전으로 멱등 적재한다. 발생 시각과 수집 시각을 따로 저장해 지연 이벤트를 구분하고, 집계 컷오프 이후 도착한 정정·취소는 해당 구간을 재계산하거나 보정한다. 스트림의 `exactly-once` 설정만으로 DW와 마트까지의 업무상 중복이 자동 해결되지는 않는다.

### [Issue] 빠른 적재와 금융성 데이터의 정합성 요구가 충돌한다

**[Solution]** 대시보드의 허용 지연과 정산·대사에 필요한 확정 시점을 분리한다. 잠정 집계에는 신선도와 확정 여부를 표시하고, 확정 집계는 원천 원장과 동일한 기준 시각·상태 정의로 대사한다. 차이가 생기면 출처, 시각 범위, 상태별 원인을 추적할 수 있어야 한다.

### [Issue] 장애를 늦게 알아차리거나 재처리가 또 다른 장애를 만든다

**[Solution]** 파이프라인별 SLO를 지연·완전성·대사 차이로 정하고, 경고 임계치와 담당자를 연결한다. 재처리에는 대상 파티션, 입력 범위, 코드·스키마 버전, 실행 ID를 남긴다. 평상시 적재와 백필이 자원을 놓고 경쟁하지 않도록 처리량 제한과 우선순위를 둔다.

## Impact & Result

공개 공고에는 빗썸의 현행 아키텍처, 처리량, 지연 시간, 개선 수치가 없다. 따라서 이 문서의 기대 효과는 **검증할 운영 지표**로만 적는다: 원천 대비 누락 건수, 중복 반영 건수, DW 반영 지연, 대사 차이, 장애 탐지·복구 시간, 재처리 성공률. 면접에서 현재 기준값과 목표 SLO를 확인해야 실제 성과를 논의할 수 있다.

## 면접에서 확인할 질문

1. 데이터 엔지니어링 조직이 직접 소유하는 경계는 원천 추출부터 DW·마트 중 어디까지인가? 원천 서비스 팀과의 데이터 계약은 어떻게 관리하는가?
2. 현재 스트림과 배치의 비중은 어떠하며, 수집 성공부터 DW 조회 가능까지의 신선도 목표는 도메인별로 다른가?
3. 주문·체결·입출금·정산 데이터의 기준 원장과 분석계 대사 기준은 무엇인가? 취소·정정과 늦은 이벤트는 어떻게 반영하는가?
4. 누락·중복·정합성 오류를 어떤 지표와 알림으로 발견하고, 재처리 범위와 멱등성을 어떻게 보장하는가?
5. 관련 공고에 나온 AWS Airflow·Redshift·Python이 이 조직에서도 운영 스택인가? 현재 공고의 Kafka·Spark·Flink 및 Lakehouse 제품은 운영 중인 것과 검토 중인 것이 각각 무엇인가?

## Reading the Diagram

그림의 화살표는 **설명용 후보 흐름**이다. 현재 공고로 확인되는 것은 `여러 원천 → DW 연계`, `ETL 설계·운영`, `품질 문제 탐지·개선`, `모니터링·알림·장애 대응`이라는 **직무 범위**다. 관련 공고는 AWS Airflow·Redshift·Python을 **우대 경험**으로 제시한다. 개별 원천, 전달 방식, Raw 계층, 제품 배치, 소비 서비스는 설계 가설이다. 자료: [현재 Data Engineer 공고](https://career.bithumbcorp.com/ko/o/219291), [관련 데이터 분석 엔지니어 공고](https://bithumbcorp.ninehire.site/job_posting/yKZg62b1). 확인일 2026-09-26.
