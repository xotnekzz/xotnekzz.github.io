### 1. 들어가며

운영중인 SeaweedFS 클러스터에서 이상한 현상이 발생했습니다. SeaweedFS 자체 메트릭에서는 디스크가 충분히 여유로워 보이는데, **실제 서버의 디스크 사용량은 거의 포화 상태**였습니다.

- SeaweedFS 메트릭: 여유 공간 충분
- 서버 디스크 메트릭: 포화 상태

처음에는 단순히 삭제된 파일의 찌꺼기가 남아있는 문제로 봤지만, 원인을 추적해보니 **SeaweedFS의 Erasure Coding(EC) 자동 변환 기능**이 문제의 핵심이었습니다. 이 글에서는 SeaweedFS의 EC 동작 원리부터 트러블 슈팅 과정, 그리고 향후 용량 관리 전략까지 정리합니다.

### 2. SeaweedFS의 볼륨 관리 구조

문제를 이해하기 위해서는 SeaweedFS가 데이터를 어떻게 저장하는지 먼저 알아야 합니다.

- **Volume**: SeaweedFS의 기본 저장 단위. 기본 30GB 크기의 큰 파일에 작은 객체들을 묶어서 저장합니다 (Haystack 방식).
- **`.dat` 파일**: 실제 데이터가 저장되는 볼륨 파일
- **`.idx` 파일**: 볼륨 내 파일들의 위치를 가리키는 인덱스
- **Filer**: 디렉토리/파일 메타데이터를 관리하는 레이어
- **Master**: 클러스터 메타데이터 및 볼륨 할당 관리

볼륨이 가득 차거나 일정 조건을 만족하면 **read-only** 상태로 전환되고, 이후 새로운 데이터는 다른 볼륨에 기록됩니다. 삭제된 파일은 즉시 디스크에서 사라지지 않고, **벡움(vacuum)** 작업을 통해 회수됩니다.

### 3. Erasure Coding(EC)이란?

Erasure Coding은 데이터를 안정적으로 분산 저장하기 위한 기법입니다.

#### 3-1. EC의 원리

SeaweedFS의 EC는 하나의 볼륨을 **14개의 조각(shard)** 으로 나눕니다.

- **10개**: 원본 데이터 조각
- **4개**: 패리티(parity) 조각

이 14개 조각 중 **최대 4개까지 손상되어도** 나머지 10개로 원본을 완벽히 복구할 수 있습니다. 14개 조각은 클러스터 내 여러 노드에 분산 저장되므로 노드 장애에도 안전합니다.

#### 3-2. 왜 EC를 쓰는가?

기존 3중화(Replication) 방식과 비교하면 EC의 장점이 분명합니다.

| 방식 | 저장 오버헤드 | 장애 허용도 |
|------|--------------|------------|
| 3중화 | 200% (원본의 3배) | 노드 2개까지 |
| EC (10+4) | 40% (원본의 1.4배) | 조각 4개까지 |

**같은 안정성을 유지하면서 저장 공간을 약 1/5 수준으로 절약**할 수 있는 효율적인 방식입니다. 그래서 대규모 콜드 데이터 보관에 적합합니다.

#### 3-3. SeaweedFS의 자동 EC 변환

SeaweedFS는 기본 설정에서 **오래된 볼륨을 자동으로 EC로 변환**합니다. 일정 기간이 지나 더 이상 자주 변경되지 않을 것으로 판단되는 read-only 볼륨을 EC로 인코딩하여 디스크 공간을 절약하려는 의도입니다.

변환 후 파일 확장자는 다음과 같이 바뀝니다.

- `.dat` (원본 볼륨) → `.ec00`, `.ec01`, ..., `.ec13` (14개 EC 조각)
- `.ecx`, `.ecj` 등의 인덱스 파일도 생성됨

### 4. 문제의 원인: EC 볼륨은 read-only

여기까지만 보면 EC는 좋은 기능처럼 보입니다. 하지만 운영 환경에서는 예상치 못한 문제를 만들어냈습니다.

#### 4-1. EC 볼륨은 수정/삭제가 불가능

EC로 변환된 볼륨은 **read-only**입니다. 즉, 이 안에 포함된 개별 파일을 삭제해도 **디스크에서 해당 공간이 회수되지 않습니다**.

- Filer에서 파일 삭제 요청 → 메타데이터는 사라짐
- 하지만 실제 EC 조각 파일은 그대로 디스크에 남아있음
- vacuum 명령어도 EC 볼륨에는 작동하지 않음

#### 4-2. 메트릭과 실제 사용량의 괴리

SeaweedFS의 메트릭은 **논리적 사용량(실제 살아있는 파일의 크기)** 을 보여주는 경우가 많습니다. 반면 서버 OS의 디스크 메트릭은 **물리적 사용량(.ec 파일들의 실제 크기)** 을 보여줍니다.

```
SeaweedFS Master UI: "디스크 여유 공간 충분"
   ↓
Filer에서 파일 삭제 (메타데이터만 제거)
   ↓
EC 조각 파일은 그대로 디스크 점유
   ↓
df -h: "디스크 포화 상태"
```

이게 바로 메트릭과 실제 사용량이 일치하지 않았던 원인이었습니다.

### 5. 해결 과정

#### 5-1. 1차 시도: vacuum

가장 먼저 시도한 것은 vacuum이었습니다.

```bash
# weed shell 진입 후
volume.vacuum
```

vacuum은 일반 볼륨에서 삭제 표시(tombstone)된 파일들을 정리하고 공간을 회수합니다. 일부 공간은 확보되었지만 EC 볼륨에는 효과가 없어 여전히 용량이 부족했습니다.

#### 5-2. 근본 원인 파악: EC 볼륨 정리

남아있는 용량의 대부분이 EC 볼륨이라는 것을 확인하고, EC 볼륨을 정리하는 방향으로 전환했습니다.

**A. 원본과 EC가 모두 존재하는 볼륨 정리**

자동 EC 변환 과정에서 `.dat` 원본 파일과 `.ec*` 조각 파일이 **둘 다 존재하는 볼륨**들이 있었습니다. 이런 경우 원본만 있어도 무방하므로 EC 조각을 삭제하여 즉시 공간을 확보할 수 있었습니다.

**B. EC → 일반 볼륨으로 디코딩**

이미 EC로만 존재하는 볼륨은 다음 절차로 정리해야 합니다.

```bash
# 1. EC 볼륨을 다시 일반 볼륨으로 디코딩
ec.decode -volumeId <id>

# 2. vacuum으로 삭제 표시된 파일들 정리
volume.vacuum -volumeId <id>

# 3. 더 이상 필요 없으면 볼륨 자체 삭제
volume.delete -volumeId <id>
```

#### 5-3. 운영 중인 대용량 데이터 선조치

가장 많은 볼륨을 차지하던 **Weblog 데이터**는 보관 가치가 시간에 반비례한다는 특성을 고려해, **TTL 60일** 설정으로 주기적으로 자동 삭제되도록 선조치했습니다.

```bash
# 볼륨 생성 시 TTL 지정 (예: 60일)
curl "http://master:9333/dir/assign?ttl=60d"
```

TTL이 설정된 볼륨은 만료 시점에 SeaweedFS가 **볼륨 단위로 통째로 삭제**하므로, vacuum이나 EC 디코딩 같은 부가 작업 없이도 자동으로 공간이 회수됩니다.

### 6. 향후 운영 방향: EC OFF + TTL 중심 관리

이번 트러블 슈팅을 거치면서 우리 환경에 맞는 운영 정책을 다음과 같이 정리했습니다.

#### 6-1. EC 비활성화

**이유:**

1. **이미 3중화로 충분한 안정성 확보**
   - 현재 클러스터는 replica 3으로 운영 중이며, 노드 2대까지 동시 장애를 허용
   - EC를 추가로 적용해도 안정성 측면에서 큰 이득이 없음
2. **데이터 자주 삭제되는 워크로드와 부적합**
   - 우리 데이터는 로그성 데이터 비중이 높고, TTL 기반으로 주기적으로 삭제됨
   - EC 변환 후 read-only가 되면 오히려 삭제 비용이 더 큼 (디코딩 필요)
3. **운영 복잡도 감소**
   - EC 변환/디코딩 같은 추가 관리 포인트가 사라짐

```bash
# Master 옵션으로 EC 자동 변환 비활성화
weed master -volumeSizeLimitMB=30000 -defaultReplication=001
# 또는 volume tier 설정에서 EC 비활성화
```

#### 6-2. TTL 기반 용량 관리

데이터 성격에 맞는 TTL을 부여해 **저장 시점에 보관 기한을 결정**하는 방식으로 전환합니다.

| 데이터 종류 | TTL | 비고 |
|------------|-----|------|
| Weblog | 60일 | 분석 사이클 기준 |
| 임시 업로드 | 7일 | 단기 캐시 |
| 영구 보관 데이터 | 없음 | 별도 관리 |

#### 6-3. 남은 EC 파일 처리

기존에 이미 변환된 EC 파일들은 점진적으로 다음 절차로 정리합니다.

1. EC 볼륨 식별 (`volume.list`로 `.ec` 파일 확인)
2. `ec.decode`로 일반 볼륨 변환
3. `volume.vacuum`으로 삭제된 데이터 회수
4. 필요 없는 볼륨은 직접 삭제

### 7. 정리

이번 SeaweedFS 디스크 트러블 슈팅에서 얻은 핵심 교훈은 다음과 같습니다.

- **메트릭의 의미를 이해하라**: SeaweedFS의 메트릭은 논리적 사용량을, OS 메트릭은 물리적 사용량을 보여준다. 두 값의 괴리는 곧 정리되지 않은 데이터가 디스크에 남아있다는 신호다.
- **자동 최적화 기능은 워크로드와 맞아야 한다**: EC는 안정적인 콜드 스토리지에는 유용하지만, 자주 삭제되는 로그성 데이터에는 오히려 독이 된다. **default 설정을 무비판적으로 받아들이지 말 것.**
- **삭제 비용까지 계산한 저장 정책**: 데이터를 어떻게 저장할지보다, **어떻게 지울지**를 먼저 설계하는 것이 운영 부담을 크게 줄여준다. TTL은 그 가장 단순하고 강력한 도구다.

분산 스토리지를 운영할 때 가장 무서운 것은 "용량이 부족하다"는 사실 자체가 아니라, "용량이 어디로 갔는지 모른다"는 가시성 부재입니다. SeaweedFS의 동작 원리를 이해하고 우리 환경에 맞게 길들이는 과정에서, 분산 스토리지를 한 단계 더 깊이 이해할 수 있었습니다.
