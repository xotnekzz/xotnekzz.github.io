### 1. "디스크가 죽었다"는 말만으로는 충분하지 않았다

SeaweedFS Volume Server 한 대에서 HDD 하나가 OS 레벨에서 이탈했다. `/storage1` 마운트가 사라졌고, 컨테이너 안에서는 그 경로가 `/data/drive1`이었다. 디스크에 있던 `.dat`, `.idx` 파일은 더 이상 읽을 수 없었다.

처음에는 단순하게 생각했다. 복제 정책이 총 3본이니, 다른 두 서버에 남은 복제본을 보고 새 복제본 하나를 만들면 끝일 것 같았다. 하지만 바로 복제를 시작하지 않았다. Master가 장애 디스크의 볼륨 위치를 아직 살아 있는 위치처럼 들고 있었기 때문이다.

분산 스토리지에서 **데이터가 실제로 있는 상태**와 **제어면이 알고 있는 상태**가 다르면, 자동 복구 도구의 출발점도 틀어진다. 이 글은 그 차이를 바로잡고, 부족 복제본을 안전하게 채운 뒤 초과본을 정리했던 경험을 기록한 글이다.

### 2. 문제를 세 부분으로 나눴다

장애 대응의 첫 단계는 "복구 명령을 찾는 일"이 아니라 사실을 분리하는 일이었다.

| 질문 | 확인 방법 | 대응 판단 |
| --- | --- | --- |
| 어느 디스크가 실제로 사라졌는가? | OS 마운트와 Volume Server 상태 | `/storage1` / `/data/drive1`을 장애 경로로 확정 |
| 어떤 볼륨이 그 경로에 있었는가? | 장애 전후 `volume.list`, Volume ID 역조회 | 142개 볼륨을 영향 범위로 확보 |
| 다른 곳에 복제본이 남아 있는가? | Master의 실제 위치 조회 | 최소 2개 생존본을 확인한 대상만 stale 해제 |

여기서 중요한 예외가 하나 있었다. Volume 188은 장애 디스크에만 있었고, 다른 Volume Server에서 생존 복제본을 찾을 수 없었다. 그렇다고 곧바로 "데이터 유실"이라고 결론 내릴 수는 없었다. FilerDB의 파일 메타데이터를 PostgreSQL 호환 커넥터로 조회했고, 제한 시간 1분 안에 참조 경로가 0건임을 확인했다.

즉 Volume 188은 현재 Filer가 참조하지 않는 orphan 데이터였다. 이 볼륨은 복구 대상에서 제외하고 Master에 다시 등록하지 않는 것으로 결정했다. 데이터 복구에서는 **복구하지 않는 결정도 증거가 있어야 한다**는 것을 다시 확인한 순간이었다.

### 3. 복구의 핵심은 stale 위치를 먼저 해제하는 것이었다

Master가 장애 디스크의 위치를 live로 계속 인식하면, 복제 부족 수가 실제보다 작게 보인다. 그래서 대상별로 다른 서버에 최소 두 개의 생존 복제본이 있다는 것을 확인한 뒤에만 stale 위치 등록을 해제했다.

그 다음에야 Master는 실제 부족 상태를 반영했다. Master의 `volume.list -v=5` 실제 위치 수를 기준으로 확인했을 때, 3본 미만인 볼륨은 154개였다. 이 값이 이후 진행률의 기준이 됐다.

![운영자, 장애 Volume Server, Master, FilerDB, 생존 Volume Server 사이의 조사·복구·검증 순서|640](/images/posts/seaweedfs3-hdd-failure-replica-recovery/replica-recovery-sequence.svg)

그림의 순서를 실제 작업에 옮기면 다음과 같다.

1. 장애 디스크의 볼륨을 역조회하고, 생존 복제본 수를 확인한다.
2. FilerDB 참조가 없는 Volume 188을 orphan으로 분기한다.
3. 장애 경로를 Volume 서비스 설정에서 제거하고, 남은 디렉터리만으로 Volume Server를 재기동한다.
4. 생존 복제본이 검증된 stale 위치만 Master에서 해제한다.
5. 부족 복제본을 먼저 채운다. 초과본 삭제는 이 단계에서 하지 않는다.
6. 3본 이상이 된 뒤에만 초과본을 별도의 승인·검증 단계에서 삭제한다.

### 4. 복구와 삭제를 같은 작업으로 묶지 않았다

처음 복제본을 채울 때는 삭제를 명시적으로 금지했다. 작업 폭도 하나로 제한했다.

```text
volume.fix.replication -apply -doDelete=false \
  -maxParallelization=1 \
  -maxParallelizationPerServer=1 \
  -volumesPerStep=1
```

이 선택에는 두 가지 이유가 있었다.

첫째, HDD 장애 직후 가장 먼저 회복해야 할 것은 **가용성 여유**다. 부족 복제본을 만들면서 초과 복제본을 동시에 삭제하면, 판단과 I/O 부하가 한 번에 얽힌다. 둘째, 대형 볼륨 복제는 오래 걸릴 수 있다. 단일 병렬로 제한하면 클러스터의 평상시 쓰기 부하와 복구 I/O를 분리해 관찰하기 쉽다.

진행 중에는 `volume.fix.replication`의 출력만으로 완료율을 계산하지 않았다. 실행 중 출력에는 같은 상태가 반복되거나, 막 등록 중인 위치가 섞일 수 있다. 대신 매번 Master의 `volume.list -v=5`에서 실제 위치 수를 세었다.

```text
정상화 진행률 = (초기 3본 미만 볼륨 수 - 현재 3본 미만 볼륨 수)
              / 초기 3본 미만 볼륨 수
```

그 결과 154개 대상 모두가 3본 이상이 됐을 때, 부족 복제본은 0개였다.

### 5. 3본 이상과 정확히 3본은 다르다

부족본을 모두 채운 뒤 무변경 검증을 실행했더니, 45개 볼륨이 4본 이상이었다. 이는 복구 과정에서 가용성을 우선한 결과다. 하지만 목표가 "적어도 3본"이 아니라 "정확히 3본"이라면 여기서 멈출 수 없다.

초과본 삭제는 별도 승인 후에만 시작했다.

```text
volume.fix.replication -apply -doDelete=true \
  -maxParallelization=1 \
  -maxParallelizationPerServer=1 \
  -volumesPerStep=1
```

`doDelete=true` 작업은 삭제 전에 남아 있는 복제본과 엔트리 동기화를 확인한다. 이 검증을 통과한 초과 복제본만 단일 병렬로 제거했다. 결과적으로 45개 초과본을 정리했고, 부족본을 다시 만들 필요 없이 정확히 3본 상태로 수렴했다.

### 6. 마지막은 복구 로그가 아니라 현재 상태로 확인했다

복구 명령이 끝났다는 메시지는 완료 증거가 아니다. 마지막에는 아래 세 가지를 다시 확인했다.

| 검증 | 확인한 내용 | 최종 결과 |
| --- | --- | ---: |
| `cluster.ps` | 연결된 Volume Server 수 | 9 |
| `volume.list -v=5` | 실제 위치 기준 under / missing / over | 0 / 0 / 0 |
| `volume.fix.replication -verbose` | 무변경 시뮬레이션의 under / misplaced / over | 0 / 0 / 0 |

Volume 188은 이 검증 과정에서도 live volume으로 재등록하거나 복제하지 않았다. orphan이라는 초기 분류를 작업 마지막까지 유지한 것이다.

### 7. 이번 장애에서 얻은 운영 원칙

이번 대응에서 남은 원칙은 명령어보다 단순하다.

#### 제어면과 데이터면을 분리해 본다

Master가 보고하는 위치가 곧 디스크에 데이터가 있다는 뜻은 아니다. OS 마운트, Volume Server 상태, Master 등록 상태를 함께 확인해야 한다. 특히 디스크가 갑자기 사라진 경우 stale 위치는 복구 부족 상태를 가린다.

#### 복구의 단위는 "볼륨"보다 "증거"다

Volume 188처럼 생존본이 없는 볼륨은 성급히 재생성할 수 없다. FilerDB 참조, 보존 요구, Master 등록 상태를 함께 봐야 복구·보류·삭제 중 하나를 선택할 수 있다.

#### 추가와 삭제는 서로 다른 변경이다

부족본 복구는 데이터 가용성을 높이는 작업이고, 초과본 정리는 데이터를 지우는 작업이다. 두 단계를 분리하고, 삭제에는 최신 시뮬레이션과 별도 승인을 둬야 한다.

#### 진행률도 현재 상태에서 계산한다

작업 도구의 로그는 진행 상황을 설명하는 데는 좋지만, 완료 판정의 근거로는 부족할 수 있다. 이번에는 Master가 실제로 보고하는 위치 수를 기준으로 154개 중 몇 개가 정상화됐는지 계산했다.

### 8. 다음 장애 전에 준비할 것

다음에는 판단 시간을 줄이고 싶다. 이를 위해 아래 항목을 운영 체크리스트로 남겼다.

1. OS 마운트 상태, Volume Server 디렉터리 상태, Master 위치 등록의 불일치를 알람으로 만든다.
2. 디스크별 Volume ID 인벤토리를 주기적으로 보관한다.
3. Master 실제 배치에서 under / missing / over / misplaced를 계산하는 점검 스크립트를 정기 실행한다.
4. 디스크 교체·재기동 시 `-dir`, `-max`, bind mount를 한 묶음으로 검증한다.
5. orphan 판정에 필요한 FilerDB 조회 절차와 보존 정책을 런북으로 고정한다.

HDD 하나가 사라진 사건은 결국 분산 스토리지의 기본을 다시 보여줬다. 복제본 수를 맞추는 일은 단순히 파일을 복사하는 작업이 아니다. **무엇이 실제로 남았는지, 무엇을 시스템이 아직 살아 있다고 믿는지, 그리고 무엇을 굳이 되살리지 않아도 되는지를 증거로 구분하는 일**이다.
