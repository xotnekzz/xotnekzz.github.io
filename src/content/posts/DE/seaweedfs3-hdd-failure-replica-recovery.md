### 1. HDD 고장을 확인한 뒤 가장 먼저 점검한 것

SeaweedFS Volume Server 한 대에서 HDD 하나가 고장나 OS 레벨에서 이탈했습니다. `/storage1` 마운트가 사라졌고, 컨테이너에서는 해당 경로를 `/data/drive1`로 사용하고 있었습니다. 디스크에 저장된 `.dat`, `.idx` 파일도 더 이상 읽을 수 없는 상태였습니다.

복제 정책은 총 3본이므로 다른 두 서버의 복제본을 이용해 새 복제본 하나를 만들면 될 것으로 예상했습니다. 하지만 Master에는 장애 디스크의 볼륨 위치가 여전히 정상 위치로 등록되어 있었습니다. 이 상태에서 복제를 실행하면 실제 복제본 수와 Master가 판단하는 복제본 수가 일치하지 않습니다. 따라서 복제 작업에 앞서 위치 정보를 바로잡아야 했습니다.

이 글에서는 실제 데이터 상태와 Master의 위치 정보가 어긋난 상황을 어떻게 확인했는지, 부족한 복제본을 채운 뒤 초과 복제본을 어떤 기준으로 정리했는지 설명합니다.

### 2. 확인할 항목을 세 가지로 나눴습니다

먼저 아래 세 가지 항목을 분리해서 확인했습니다.

| 질문 | 확인 방법 | 대응 판단 |
| --- | --- | --- |
| 어느 디스크가 실제로 사라졌는가? | OS 마운트와 Volume Server 상태 | `/storage1` / `/data/drive1`을 장애 경로로 확정 |
| 어떤 볼륨이 그 경로에 있었는가? | 장애 전후 `volume.list`, Volume ID 역조회 | 142개 볼륨을 영향 범위로 확보 |
| 다른 곳에 복제본이 남아 있는가? | Master의 실제 위치 조회 | 최소 2개 생존본을 확인한 대상만 stale 해제 |

Volume 188은 별도로 확인해야 했습니다. 이 볼륨은 장애 디스크에만 있었으며, 다른 Volume Server에서는 복제본을 찾을 수 없었습니다. 다만 복제본이 없다는 사실만으로 데이터 유실이라고 판단하지는 않았습니다. FilerDB의 파일 메타데이터를 PostgreSQL 호환 커넥터로 조회한 결과, 제한 시간 1분 안에 확인된 참조 경로는 0건이었습니다.

Volume 188은 현재 Filer가 참조하지 않는 orphan 데이터로 판단했습니다. 따라서 복구 대상에서 제외하고 Master에도 다시 등록하지 않기로 했습니다. 복구 대상에서 제외할 때도 FilerDB 조회 결과와 같은 확인 근거를 남겼습니다.

### 3. stale 위치를 먼저 해제했습니다

Master가 장애 디스크의 위치를 live 상태로 계속 인식하면 복제본 부족 수가 실제보다 작게 집계됩니다. 각 볼륨에 대해 다른 서버에 최소 두 개의 정상 복제본이 남아 있는지 확인한 뒤 stale 위치 등록을 해제했습니다.

위치 등록을 해제한 뒤에야 Master에 실제 부족 상태가 반영되었습니다. `volume.list -v=5`의 실제 위치 수를 기준으로 집계한 결과, 복제본이 3개 미만인 볼륨은 154개였습니다. 이후 복구 진행률은 이 수치를 기준으로 계산했습니다.

![운영자, 장애 Volume Server, Master, FilerDB, 생존 Volume Server 사이의 조사·복구·검증 순서|640](/images/posts/seaweedfs3-hdd-failure-replica-recovery/replica-recovery-sequence.svg)

실제 작업은 다음 순서로 진행했습니다.

1. 장애 디스크의 볼륨을 역조회하고 생존 복제본 수를 확인했습니다.
2. FilerDB 참조가 없는 Volume 188을 orphan으로 분류했습니다.
3. 장애 경로를 Volume 서비스 설정에서 제거하고 남은 디렉터리만으로 Volume Server를 재기동했습니다.
4. 생존 복제본이 확인된 볼륨의 stale 위치만 Master에서 해제했습니다.
5. 부족한 복제본부터 생성하고, 이 단계에서는 초과 복제본을 삭제하지 않았습니다.
6. 모든 볼륨이 3본 이상이 된 뒤 별도의 승인과 검증을 거쳐 초과 복제본을 삭제했습니다.

### 4. 복구와 삭제를 별도로 진행했습니다

부족한 복제본을 생성하는 동안에는 삭제 옵션을 비활성화했습니다. 병렬 처리 수도 1로 제한했습니다.

```text
volume.fix.replication -apply -doDelete=false \
  -maxParallelization=1 \
  -maxParallelizationPerServer=1 \
  -volumesPerStep=1
```

이렇게 설정한 이유는 두 가지입니다.

첫째, HDD 장애 직후에는 부족한 복제본을 먼저 확보해야 합니다. 복제본 생성과 초과 복제본 삭제를 동시에 수행하면 변경 범위가 커지고 I/O 부하의 원인도 구분하기 어려워집니다. 둘째, 대형 볼륨의 복제에는 시간이 오래 걸릴 수 있습니다. 병렬 처리를 1로 제한하면 평상시 쓰기 부하와 복구 I/O를 구분해 관찰하기 수월합니다.

진행률은 `volume.fix.replication`의 출력만으로 계산하지 않았습니다. 실행 로그에는 같은 상태가 반복되거나 새로 등록 중인 위치가 포함될 수 있기 때문입니다. 대신 Master의 `volume.list -v=5`를 조회해 실제 위치 수를 집계했습니다.

```text
정상화 진행률 = (초기 3본 미만 볼륨 수 - 현재 3본 미만 볼륨 수)
              / 초기 3본 미만 볼륨 수
```

154개 대상이 모두 3본 이상이 된 시점에 부족 복제본이 0개인 것을 확인했습니다.

### 5. 복제본 수를 정확히 3본으로 맞췄습니다

부족한 복제본을 모두 채운 뒤 무변경 검증을 실행한 결과, 45개 볼륨에 복제본이 4개 이상 존재했습니다. 복구 단계에서 기존 복제본을 삭제하지 않았기 때문에 생긴 결과입니다. 운영 정책은 볼륨당 정확히 3본이므로 초과 복제본을 별도로 정리했습니다.

초과 복제본 삭제는 별도 승인을 받은 뒤 시작했습니다.

```text
volume.fix.replication -apply -doDelete=true \
  -maxParallelization=1 \
  -maxParallelizationPerServer=1 \
  -volumesPerStep=1
```

`doDelete=true` 작업은 삭제 전에 남은 복제본과 엔트리의 동기화 상태를 확인합니다. 이 검증을 통과한 초과 복제본만 하나씩 제거했습니다. 총 45개의 초과 복제본을 정리했으며, 모든 대상 볼륨의 복제본 수가 3개로 맞춰졌습니다.

### 6. 복구 후 현재 상태를 다시 확인했습니다

복구 명령의 종료 메시지만으로 작업 완료를 판단하지 않았습니다. 마지막으로 아래 세 가지 상태를 다시 확인했습니다.

| 검증 | 확인한 내용 | 최종 결과 |
| --- | --- | ---: |
| `cluster.ps` | 연결된 Volume Server 수 | 9 |
| `volume.list -v=5` | 실제 위치 기준 under / missing / over | 0 / 0 / 0 |
| `volume.fix.replication -verbose` | 무변경 시뮬레이션의 under / misplaced / over | 0 / 0 / 0 |

Volume 188은 검증 과정에서도 live volume으로 재등록하거나 복제하지 않았습니다. 처음 확인한 orphan 분류를 그대로 유지했습니다.

### 7. 이후 운영에 반영한 사항

이번 장애 대응 이후 다음 기준을 운영 절차에 반영했습니다.

#### 제어면과 데이터면을 함께 확인합니다

Master에 위치가 등록되어 있어도 디스크에 실제 데이터가 남아 있다고 단정할 수 없습니다. OS 마운트, Volume Server 상태, Master 등록 상태를 함께 확인해야 합니다. 디스크가 갑자기 이탈하면 stale 위치 때문에 복제본 부족 상태가 드러나지 않을 수 있습니다.

#### 복구 여부는 확인 근거를 바탕으로 결정합니다

Volume 188처럼 정상 복제본이 없는 볼륨을 바로 재생성해서는 안 됩니다. FilerDB 참조 여부, 데이터 보존 요구 사항, Master 등록 상태를 함께 확인한 뒤 복구·보류·삭제 중 하나를 선택해야 합니다.

#### 복제본 생성과 삭제를 분리합니다

부족한 복제본을 생성하는 작업은 가용성을 높이지만, 초과 복제본 정리는 데이터를 삭제합니다. 두 단계를 분리하고 삭제 전에는 최신 상태를 기준으로 시뮬레이션한 뒤 별도 승인을 받아야 합니다.

#### 진행률은 현재 상태를 기준으로 계산합니다

작업 로그만으로는 완료 여부를 정확히 판단하기 어렵습니다. 이번 작업에서는 Master가 보고하는 실제 위치 수를 기준으로 154개 볼륨 중 몇 개가 정상화되었는지 계산했습니다.

### 8. 추가로 준비할 사항

비슷한 장애가 발생했을 때 확인 시간을 줄일 수 있도록 아래 항목을 운영 체크리스트에 추가했습니다.

1. OS 마운트 상태, Volume Server 디렉터리 상태, Master 위치 등록 사이의 불일치를 감지하는 알람을 구성합니다.
2. 디스크별 Volume ID 인벤토리를 주기적으로 보관합니다.
3. Master의 실제 배치를 기준으로 under / missing / over / misplaced 상태를 계산하는 점검 스크립트를 정기적으로 실행합니다.
4. 디스크 교체 또는 재기동 시 `-dir`, `-max`, bind mount 설정을 함께 검증합니다.
5. orphan 판정에 필요한 FilerDB 조회 절차와 데이터 보존 정책을 런북에 명시합니다.

이번 작업에서는 복제를 시작하기 전에 실제 데이터 상태와 Master의 위치 정보를 먼저 일치시키는 것이 중요했습니다. 이후에도 디스크 장애가 발생하면 생존 복제본, stale 위치, FilerDB 참조 여부를 각각 확인한 뒤 복구 범위를 정할 예정입니다.
