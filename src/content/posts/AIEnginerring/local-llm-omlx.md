## 배경

Gemini API 비용이 인상됨에 따라 새로운 대안이 필요해졌습니다.

사내에서는 GitLab 코드 리뷰, GitLab 자동 Release 생성, WatchDog(이메일 분류) 등 Gemini API를 사용하여 AI를 활용한 업무 도구를 운영하고 있습니다. 비용을 줄이기 위해 몇 가지 대안을 검토했습니다.

**1) 구독 플랜 전환** — Pro, Max(Ultra) 등 구독 옵션이 API 대비 20배 이상 효율적이지만, Google Generative AI 등 SDK 방식은 구독 플랜의 OAuth2 인증을 지원하지 않아 기존 자동화 파이프라인에 적용할 수 없었습니다.

**2) OpenRouter** — 가성비 모델(Deepseek-v4-flash)을 사용하는 방법으로, 비용 면에서는 최고의 대안이었습니다.

**3) Local LLM** — 사내에 보유 중인 맥스튜디오(M2 Ultra 192GB)가 유휴 상태였고, 코드 리뷰나 이메일 분류 같은 작업은 최신 클라우드 모델 수준의 성능이 필요하지 않아 로컬 LLM으로도 충분히 대체할 수 있을 것으로 판단했습니다. 외부 API 의존 없이 사내망에서 바로 서빙할 수 있다는 점도 장점이었습니다.

이 글에서는 3번, Local LLM 기반 AI 추론 서버를 도입한 과정을 공유합니다.

## 모델 선택

어떤 오픈 모델이 맥스튜디오에서 쾌적하게 돌아갈 수 있을지 조사한 결과, `Qwen3.6-35b-a3b` 모델을 선택했습니다.

이 모델은 MoE(Mixture of Experts) 아키텍처를 사용합니다. 35b(350억 개) 파라미터로 학습되었지만, 추론 시에는 3b(30억 개) 파라미터만 활성화하여 작동하기 때문에 메모리를 많이 점유하지 않으면서도 빠른 토큰 속도를 지원합니다.

##### MoE 아키텍처란

하나의 거대한 인공지능 모델을 여러 개의 작은 '전문가(Expert)' 네트워크로 나누고, 입력된 데이터나 질문에 따라 가장 적합한 전문가만 선택적으로 활성화하여 처리하는 아키텍처입니다.

##### 양자화(Quantization)

모델명에 `Qwen3.6-35b-a3b-4bit` 또는 `Qwen3.6-35b-a3b-8bit`처럼 bit가 뒤에 붙는데, 이는 양자화 모델입니다. 양자화란 16bit, 32bit 단위로 숫자를 연산하여 막대한 메모리(VRAM)가 필요한 모델을 8bit 또는 4bit로 압축하여 모델의 크기와 요구 메모리를 줄이는 기술입니다.

- **8bit** - 원본 모델 대비 성능 저하가 거의 없이 메모리 요구량을 절반 수준으로 줄여줍니다.
- **4bit** - 미세한 답변의 질이 떨어질 수 있으나 메모리 사용량을 1/4 수준으로 낮춰줍니다.

`Qwen3.6-35b-a3b` 모델 기준 8bit 사용 시 약 40GB, 4bit 사용 시 약 20GB 정도 메모리를 점유합니다. 맥스튜디오가 192GB라는 넉넉한 메모리를 가지고 있으므로, 성능 손실이 적은 `Qwen3.6-35b-a3b-8bit` 모델을 최종으로 선택하였습니다.

## 런타임 선택: llama.cpp vs MLX

모델을 선택했으니, 다음은 이 모델을 어떤 런타임 위에서 돌릴 것인지 결정해야 합니다.

##### llama.cpp
메타의 LLaMA 모델을 일반 사용자의 컴퓨터에서 돌아가게끔 만들어진 오픈소스 프로젝트입니다.
모든 플랫폼(Mac, Windows, Linux, Android 등)에서 사용 가능하며, 다양한 하드웨어에서 가볍고 빠른 추론 및 서빙이 가능합니다. GGUF 포맷을 지원합니다.

##### MLX
Apple의 AI 연구팀이 직접 만든 머신러닝 프레임워크입니다. Apple 생태계에 특화된 파이토치(PyTorch)라고 볼 수 있습니다.

Apple Silicon 칩에는 CPU, GPU, AI 연산을 위한 NPU가 하나로 합쳐진 통합 메모리 구조입니다. MLX는 이 구조를 완벽하게 이해하고 만들어졌기 때문에, AI를 돌릴 때 메모리를 복사하지 않고(Zero Copy) 낭비 없이 빠른 속도와 높은 전력 효율을 보여줍니다.

우리 장비가 M2 Ultra(Apple Silicon)인 만큼 통합 메모리의 Zero Copy 이점을 최대한 활용할 수 있는 **MLX**를 런타임으로 선택했습니다.

## 서빙 도구 선택: LM Studio에서 oMLX로

런타임을 MLX로 결정한 뒤, 이 모델을 API 서버로 서빙할 도구를 찾아야 했습니다.

##### LM Studio 시도

로컬 LLM을 구동하는 도구로 LM Studio와 Ollama가 범용적으로 많이 사용됩니다.

- **LM Studio** — GUI를 통해 Local LLM을 실행할 수 있는 데스크톱 애플리케이션입니다. 모델 검색, 모델 전환, 채팅 기능 등 사용자 편의성에 중점을 두었으며, 로컬 서버를 실행하여 다른 도구에서 호출할 수도 있습니다.
- **Ollama** — 명령줄 워크플로우와 로컬 HTTP API를 통해 LLM을 다운로드하고 실행할 수 있도록 도와주는 도구입니다.

`Qwen3.6-35b-a3b-8bit` 모델로 둘 다 사용해 본 결과, LM Studio가 모델 검색과 서버 구동 등 편리한 GUI를 제공하며 로컬 서버의 응답 속도가 더 빨라 LM Studio를 먼저 채택했습니다.

##### LM Studio의 한계

그런데 LM Studio에서 MLX 모델로 서버를 배포하면 **동시성이 1로 제한**되는 한계가 있었습니다. 모델이 리즈닝 무한 반복에 빠져 대답을 못하고 있으면, 이후에 들어오는 요청이 큐에 계속 쌓이게 됩니다. 코드 리뷰와 이메일 분류가 동시에 요청되는 상황에서 이는 치명적이었습니다.

##### oMLX 도입

MLX 기반으로 동시 서빙을 잘 처리할 수 있는 프레임워크를 찾은 결과, **oMLX**를 발견했습니다.

oMLX는 Apple Silicon 기반 Mac 환경에서 LLM을 가장 빠르고 효율적으로 실행할 수 있도록 설계된 로컬 AI 추론 서버 플랫폼입니다. MLX를 기반으로 실제 서비스 운영 환경처럼 편리하게 쓸 수 있도록 운영 체계와 사용자 인터페이스를 덧붙인 제품입니다.

oMLX가 LM Studio 대비 갖는 핵심 장점은 다음과 같습니다.

- **Two-Tier KV Cache**
  컨텍스트가 길어지면 메모리(VRAM) 부족으로 맥이 느려지거나 멈추는 병목 현상이 발생합니다. oMLX는 자주 쓰는 데이터는 메모리(Hot Cache)에 두고, 당장 쓰지 않는 과거 대화 맥락은 SSD(Cold Cache)로 빼두는 2단계 KV 캐시 기술을 사용하여 이 문제를 해결합니다.

- **Continuous Batching**
  답변이 끝난 요청은 즉시 내보내고 새 요청을 실시간으로 채워 넣어, 맥의 자원을 쉬지 않고 효율적으로 가동합니다. LM Studio에서 겪었던 동시성 1 제한 문제가 근본적으로 해결됩니다.

- **PagedAttention 알고리즘**
  메모리를 잘게 쪼개어 가상으로 관리함으로써 낭비를 없애고, 동시 처리가 많아져도 RAM이 가득 차는 파편화 문제를 해결합니다.

## 실제 활용

![](/images/posts/local-llm-omlx/img-1.png)

oMLX가 제공하는 Admin 페이지입니다. AI 추론 서버의 성능을 실시간으로 모니터링할 수 있습니다.

`Qwen3.6-35B-A3B-8bit` 모델로 코드 리뷰, 메일 자동 분석 등을 서빙하고 있으며, 초당 토큰 생성이 51.5 tok/s로 나쁘지 않은 성능입니다.

![](/images/posts/local-llm-omlx/img-2.png)

LM Studio처럼 원하는 모델을 허깅페이스를 통해 다운로드받을 수 있습니다.

![](/images/posts/local-llm-omlx/img-3.png)

Two-Tier KV Cache, 동시성 제어 등을 설정할 수 있는 UI를 제공합니다. 앞서 언급한 동시성 문제를 이 설정을 통해 해결할 수 있었습니다.

![](/images/posts/local-llm-omlx/img-4.png)

벤치마크 기능을 제공하여, 하드웨어에 적합한 모델을 테스트해 볼 수 있습니다.

## 결론

이번 도입을 통해 GitLab 코드 리뷰, 자동 Release 생성, 이메일 자동 분류 등 기존 Gemini API 기반 업무 도구를 Local LLM으로 대체할 수 있었습니다. 51.5 tok/s의 응답 속도는 사내 자동화 용도로 충분했고, oMLX의 동시 처리 덕분에 여러 요청이 동시에 들어와도 안정적으로 서빙되고 있습니다.

물론 Opus 4.7, Gemini 3.1 Pro, GPT 5.5 등 클라우드 모델과 비교하면 복잡한 추론이나 긴 맥락 이해에서 차이를 느낄 수 있습니다. 하지만 정형화된 업무 자동화 수준에서는 충분히 실용적이었습니다.

Local Model이 예전보다 크게 경량화되었고, Apple Silicon에 최적화된 MLX와 이를 추론 서버로 서빙하는 oMLX 같은 도구의 등장으로, 유휴 장비만 있다면 로컬 LLM 도입을 충분히 고려해 볼 만하다고 생각합니다.
