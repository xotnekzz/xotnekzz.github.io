# 컬리·빗썸 데이터 엔지니어 예상 면접 Q&A

## 답변 원칙

- 결론을 먼저 말하고 `문제 → 판단 → 실행 → 결과 → 한계` 순서로 답한다.
- 직접 운영한 것, 팀원이 구현한 것, PoC인 것을 명확히 구분한다.
- BigQuery, Flink, Kafka, EKS, Iceberg처럼 직접 운영하지 않은 기술은 경험을 부풀리지 않는다.
- 성과 수치는 측정 조건과 계산 근거를 함께 말한다. 근거가 부족하면 추정치임을 밝힌다.
- 답변은 1~2분을 기본으로 하고, 세부 구현은 꼬리 질문에서 설명한다.

---

## 1. 공통 질문

### Q1. 간단히 자기소개해 주세요.

**A.**

안녕하세요. 데이터 플랫폼의 구축과 운영, 분석 파이프라인, 거버넌스를 함께 다뤄온 데이터 엔지니어 김태수입니다.

비트망고에서 약 7년간 근무하며 10년 이상 운영된 HDFS·Impala 환경을 SeaweedFS와 Apache Doris 기반 플랫폼으로 전환했습니다. 이 과정에서 로그 수집 구조, Airflow 파이프라인, 데이터 모델링과 BI 환경까지 함께 개선했습니다. 현재는 3명의 팀원과 데이터 파트를 운영하며 OpenMetadata 기반의 계보·소유권·품질 체계를 구축하고 있습니다.

최근에는 이 거버넌스 정보를 AI 에이전트가 활용하도록 연결해 데이터 탐색, 분석, 장애 대응과 같은 반복 업무를 자동화하고 있습니다. 저는 특정 제품을 운영하는 것보다, 데이터가 신뢰할 수 있는 형태로 생산되고 실제 업무에 사용되도록 전체 구조를 설계하는 데 강점이 있습니다.

### Q2. 현재 이직하려는 이유는 무엇인가요?

**A.**

현재 회사에서 레거시 플랫폼 전환과 거버넌스 기반 구축을 주도하며 기술적으로 의미 있는 경험을 했습니다. 다음 단계에서는 더 큰 데이터 규모와 다양한 데이터 소스, 높은 신뢰성 요구가 있는 환경에서 제 경험을 확장하고 싶습니다.

특히 제가 해온 플랫폼 현대화, 반복 운영 자동화, 데이터 품질과 계보 구축이 컬리와 빗썸의 채용 과제와 직접 연결되어 있다고 판단했습니다. 단순히 새로운 기술을 사용하고 싶은 것이 아니라, 지금까지 해결해 온 문제를 더 복잡하고 중요한 환경에서 풀어보고 싶어 지원했습니다.

### Q3. 본인의 가장 큰 강점은 무엇인가요?

**A.**

저의 가장 큰 강점은 문제를 정의하는 데 그치지 않고, 조직과 인프라 환경을 고려해 현실적인 해결책을 선택하고 끝까지 실행하는 능력입니다.

데이터팀의 선임 구성원들이 퇴사하면서 기존 핵심 플랫폼인 HDFS·Impala의 운영 리스크가 커졌습니다. 동시에 데이터 거버넌스가 정립되지 않아 퇴사자들이 남긴 테이블, 데이터베이스와 파이프라인이 파편화되어 있었고, 반복되는 장애와 유지보수로 인해 팀이 새로운 업무에 집중하기 어려운 상황이었습니다.

저는 이를 개별 장애가 아니라 플랫폼과 데이터 관리 체계의 문제로 정의했습니다. 먼저 당시의 인력과 기존 서버 환경에서 운영할 수 있는 Doris·SeaweedFS 기반의 레이크하우스 구조를 설계하고 마이그레이션을 주도했습니다. 그 위에 메달리온 아키텍처를 적용해 원천 데이터는 Bronze, 정제·표준화 데이터는 Silver, 업무용 마트는 Gold로 역할을 구분했으며, dbt를 도입해 마트 모델링 방식을 표준화했습니다.

마지막으로 OpenMetadata를 도입해 메타데이터 자동 수집, 데이터 자산 명세, 소유권, 계보와 데이터 품질을 하나의 체계로 연결했습니다. 이처럼 저는 눈앞의 장애만 해결하는 것이 아니라, 주어진 환경에 맞는 기술과 운영 방식을 선택해 팀이 반복적인 유지보수에서 벗어나 새로운 일을 할 수 있는 기반까지 만드는 데 강점이 있습니다.

### Q4. 가장 대표적인 프로젝트를 설명해 주세요.

**A.**

가장 대표적인 프로젝트는 40대의 기존 서버를 재활용해 HDFS·Impala 기반 데이터 환경을 SeaweedFS와 Apache Doris 기반으로 전환한 프로젝트입니다.

기존 환경은 노후화와 기술 지원 부담이 있었고, 대규모 쿼리에서 네트워크 I/O 병목이 컸습니다. 신규 장비 구매가 어려웠기 때문에 기존 장비의 역할을 재배치했습니다. 9대는 SeaweedFS, 3대는 Doris FE, 28대는 Doris BE로 구성하고, 로그 ETL도 DuckDB와 Parquet 중심으로 단순화했습니다.

그 결과 특정 단순 집계 쿼리는 85초에서 50ms 이내로, 복잡한 조인 집계는 250초에서 약 40초로 개선했습니다. 이 프로젝트에서 제가 가장 중요하게 본 것은 엔진 교체 자체가 아니라 데이터 수집부터 분석까지 운영 단계를 줄이고, 제한된 자원 안에서 성능과 복구 가능성을 함께 확보하는 것이었습니다.

### Q5. 왜 Apache Doris를 선택했나요?

**A.**

주요 요구사항은 수백억 건의 로그에 대한 빠른 집계, 기존 서버의 재활용, BI 도구와의 SQL 호환성, 그리고 소규모 팀이 운영할 수 있는 구조였습니다.

기존 Impala 구조는 쿼리 시 공유 스토리지에서 데이터를 읽어오는 네트워크 비용이 컸습니다. Doris는 데이터와 연산을 BE에 함께 배치하는 Shared Nothing 구조이고, 분산·복제·사전 집계 기능을 제공해 현재 병목을 직접 해결할 수 있다고 판단했습니다.

과거 MariaDB ColumnStore에서 StarRocks로 전환해 성능을 개선한 경험도 의사결정 근거로 활용했습니다. 다만 Doris를 모든 문제의 정답으로 본 것은 아닙니다. 고빈도 point lookup이나 트랜잭션 처리보다는 대규모 분석 쿼리에 적합했고, compaction과 데이터 분포, 디스크 운영을 직접 관리해야 한다는 비용도 함께 고려했습니다.

### Q6. 85초에서 50ms로 개선했다는 수치는 어떻게 검증했나요?

**A.**

동일한 분석 목적의 조건 집계 쿼리를 기준으로 기존 Impala와 Doris의 응답 시간을 비교했습니다. 해당 수치는 특정 단순 집계 쿼리의 대표 사례이고, 모든 쿼리가 동일한 비율로 개선된 것은 아닙니다. 복잡한 조인 집계의 경우에는 250초에서 약 40초로 개선됐습니다.

면접에서는 최대 개선 수치만 강조하기보다 쿼리 유형별 결과를 구분해서 말씀드리겠습니다. 또한 캐시 상태, 동시 사용자 수, 데이터 분포에 따라 결과가 달라질 수 있으므로, 이를 플랫폼 전체의 일반적인 성능 향상률이라고 표현하지 않겠습니다.

> **면접 전 보완:** 테스트 데이터 건수, cold/warm cache 조건, 반복 횟수, 평균·p95, 동시성 조건을 실제 기록으로 확인한다.

### Q7. FE 3대와 BE 28대로 구성한 이유는 무엇인가요?

**A.**

FE는 메타데이터와 쿼리 계획을 담당하므로 고가용성을 위해 3대로 구성했습니다. 홀수 quorum을 유지해 한 대 장애에도 메타데이터 서비스를 지속할 수 있게 한 것입니다.

BE는 실제 데이터 저장과 연산을 담당하므로 사용 가능한 장비 중 디스크 용량과 연산 자원을 고려해 28대를 배치했습니다. 데이터 복제와 분산을 통해 일부 BE 장애에도 조회와 적재가 지속되도록 구성했습니다.

노드 수 자체가 목표라기보다, 기존 40대의 사양과 장애 도메인을 확인한 뒤 저장 계층과 연산 계층에 필요한 자원을 배분한 결과입니다.

> **면접 전 보완:** replication 수, rack 또는 장애 도메인 분리 방식, BE 한 대 장애 시 실제 복구 절차와 소요 시간을 확인한다.

### Q8. 마이그레이션 과정에서 데이터 정합성을 어떻게 검증했나요?

**A.**

마이그레이션은 한 번에 전환하기보다 기존 경로와 신규 경로를 병행해 비교하는 방식이 안전하다고 판단했습니다. 파티션 단위의 건수, 핵심 지표 집계, null과 distinct key 수를 비교하고 차이가 발생한 파티션을 다시 추적하는 방식으로 검증했습니다.

신규 테이블을 바로 기준 데이터로 사용하지 않고 검증 기간을 둔 뒤 BI와 downstream 소비자를 단계적으로 전환하는 것이 핵심입니다. 또한 원본 로그를 gzip 형태로 유지해 변환 로직에 문제가 생겼을 때 다시 처리할 수 있도록 했습니다.

> **면접 전 보완:** 실제 병행 운영 기간, 검증 SQL, 허용 오차, 컷오버와 롤백 절차를 확인한다.

### Q9. DuckDB를 선택하고 Spark를 사용하지 않은 이유는 무엇인가요?

**A.**

기술의 인지도보다 실제 처리 단위와 운영 비용을 기준으로 선택했습니다.

시간당 입력 파일은 로그 서버별 최대 약 800MB에서 1GB였고, 세 서버의 파일을 병렬로 처리했습니다. 기존 ETL 서버에는 500GB 메모리가 있었으며 세 작업을 동시에 실행했을 때 서버 전체 메모리 사용률이 약 30~39%였습니다. 이 규모에서는 Spark 클러스터를 추가로 구축하고 운영하는 비용보다 DuckDB의 단일 노드 벡터화 실행이 더 단순하고 충분하다고 판단했습니다.

다만 입력이 단일 노드 메모리와 디스크 처리 범위를 넘어가거나, 지속적인 스트림 상태 처리와 초 단위 지연이 필요해진다면 Spark 또는 Flink를 다시 검토해야 합니다.

### Q10. DuckDB ETL은 재실행 시 중복되지 않나요?

**A.**

분석 기준 날짜인 `logdate`와 재처리 기준인 KST 입력 배치 `inputdatetime`, 서버 ID를 분리해 처리 범위를 식별했습니다. 같은 입력 배치와 서버를 다시 처리할 때는 새 Parquet 저장이 성공한 뒤 해당 배치·서버의 기존 파일을 정리하도록 했습니다.

ETL은 실제로 생성한 `(logdate, inputdatetime)` 목록을 반환하고, Airflow가 그 결과를 downstream 적재 범위로 사용합니다. 업로드가 실패하면 성공 이벤트를 발행하지 않습니다.

현재 구현은 전체 배치를 하나의 트랜잭션으로 교체하는 완전한 atomic 구조는 아닙니다. 따라서 더 높은 정합성이 필요한 환경이라면 임시 경로에 먼저 작성하고 검증 후 manifest 또는 snapshot pointer를 교체하는 방식을 추가하겠습니다.

### Q11. 0건인 배치에서는 왜 기존 데이터를 유지하나요?

**A.**

0건이 실제로 이벤트가 없는 정상 상태인지, 입력 누락이나 파싱 오류로 인해 발생한 상태인지 즉시 구분하기 어려웠기 때문입니다. 0건 결과로 기존 데이터를 덮어쓰면 정상 데이터를 삭제할 위험이 더 크다고 판단했습니다.

따라서 0건이면 기존 결과를 유지하고 별도 검증과 알림 대상으로 처리했습니다. 더 발전시킨다면 원천 파일 존재 여부, 파일 크기, 파싱 실패 건수와 upstream 완료 신호를 함께 확인한 뒤 정상적인 0건인지 판정하겠습니다.

### Q12. Airflow Cron 파이프라인을 Asset 기반으로 바꾼 이유는 무엇인가요?

**A.**

Cron은 실행 시각만 보장하고 입력 데이터가 준비됐는지는 보장하지 않기 때문입니다. 기존에는 upstream 데이터가 늦게 도착해도 downstream이 정해진 시각에 실행됐고, 누락 복구 시 운영자가 영향받은 DAG를 찾아 순서대로 재실행해야 했습니다.

업스트림 처리 완료 시 Asset 이벤트를 발행하고 downstream이 이를 실행 조건으로 사용하도록 변경했습니다. 이후 partition key를 이벤트에 포함해 정기 배치와 백필이 같은 처리 단위를 사용하도록 개선했습니다. 이를 통해 실행 시각보다 실제 데이터 준비 상태를 파이프라인의 기준으로 삼았습니다.

### Q13. Asset Partition Key가 멱등성을 보장하나요?

**A.**

아닙니다. Partition Key는 어떤 입력 범위를 처리해야 하는지를 명확히 식별할 뿐입니다. 같은 키를 여러 번 처리해도 동일한 결과가 나오는지는 sink의 적재 방식이 보장해야 합니다.

따라서 partition key를 overwrite 범위나 merge 조건으로 사용하고, 이벤트 발행도 실제 적재가 완료된 후에 수행해야 합니다. 저는 Asset 이벤트와 데이터 처리의 멱등성을 구분해서 설명합니다.

### Q14. 여러 upstream Asset이 있는 경우에는 어떻게 처리하나요?

**A.**

단순히 이벤트 하나가 도착했다고 실행하면 안 됩니다. 같은 partition key에 필요한 모든 upstream 데이터가 준비됐는지 확인해야 합니다.

각 upstream의 완료 상태를 key 기준으로 기록하고, 필요한 입력 조건이 모두 충족됐을 때 downstream을 실행하는 방식이 필요합니다. 이벤트가 중복되거나 순서가 바뀌어도 key 기반 상태로 판단하며, 오래 도착하지 않는 입력에는 SLA와 별도 알림을 설정합니다.

### Q15. OpenMetadata를 도입한 이유는 무엇인가요?

**A.**

데이터베이스, Airflow, 소유권, 설명, 품질 정보가 서로 분리되어 있었고, 소규모 데이터팀이 모든 자산의 의미를 대신 관리할 수 없었기 때문입니다.

OpenMetadata는 검색, 계보, 소유권, Glossary, 프로파일링과 품질 결과를 하나의 플랫폼에서 연결할 수 있었습니다. DataHub와 Amundsen도 비교했지만, 현재 팀 규모에서는 여러 구성 요소를 별도로 운영하는 것보다 통합 기능과 API 확장성이 중요했습니다.

기술 메타데이터는 자동 수집하고 비즈니스 의미와 소유권은 도메인 담당자가 관리하도록 책임을 분리한 것이 핵심입니다.

### Q16. OpenLineage로 전환한 이유는 무엇인가요?

**A.**

초기에는 Airflow 2.9.3과 당시 연동 모듈의 버전 충돌 때문에 커스텀 데코레이터가 OpenMetadata API를 직접 호출하도록 구현했습니다. 빠르게 적용할 수 있었지만 OpenMetadata의 API와 내부 모델에 결합되는 유지보수 문제가 있었습니다.

Airflow 3 전환 후에는 실행 컨텍스트에서 입출력 자산을 추출하는 적용 방식은 유지하되, 내부 전달을 OpenLineage 표준 이벤트로 변경했습니다. Airflow는 계보 이벤트 생성에 집중하고 OpenMetadata는 이를 자산과 연결하도록 책임을 분리했습니다.

### Q17. 데이터 메시와 데이터 카탈로그의 차이는 무엇인가요?

**A.**

데이터 카탈로그는 데이터 메시를 지원하는 도구 중 하나일 뿐입니다. 데이터 메시는 도메인이 데이터를 제품처럼 소유하고, 중앙 플랫폼팀이 셀프서비스 기반을 제공하며, 공통 표준을 연합 거버넌스로 운영하는 조직·아키텍처 모델입니다.

OpenMetadata를 설치했다고 데이터 메시가 완성되는 것은 아닙니다. 소유권, SLO, 데이터 계약, 접근 정책과 변경 책임이 실제 도메인 운영 방식에 포함되어야 합니다. 현재 경험은 그중 자산 검색, 계보, 소유권과 공통 용어 기반을 마련한 단계라고 설명하겠습니다.

### Q18. Data Quality as Code는 어떻게 운영하나요?

**A.**

품질 규칙을 코드와 설정으로 관리해 변경 이력과 리뷰가 가능하도록 하는 방식입니다. 입력 이전에는 파일 존재 여부, 스키마, 크기와 freshness를 확인하고, 적재 이후에는 row count, null, unique, 허용 범위와 참조 무결성을 검사합니다.

모든 실패를 동일하게 차단하지는 않습니다. 핵심 키 중복이나 필수 컬럼 null처럼 downstream 결과를 신뢰할 수 없게 만드는 오류는 적재 또는 이벤트 발행을 차단합니다. 분포 변화처럼 즉시 오류라고 확정하기 어려운 검사는 경고로 운영하고 추세를 함께 확인합니다.

### Q19. Prometheus와 Grafana를 도입해 무엇이 달라졌나요?

**A.**

기존에는 Munin에서 서버 메트릭을 보고 Icinga2에서 장애 알림을 관리해, 컨테이너와 데이터 플랫폼 내부 상태를 함께 보기 어려웠습니다.

node_exporter, cAdvisor, Doris와 SeaweedFS의 native metric을 Prometheus로 통합하고 Grafana에서 대시보드와 알림을 함께 운영했습니다. 이로써 호스트, 컨테이너, 애플리케이션 계층을 같은 시간축에서 볼 수 있게 됐습니다.

다만 인프라 메트릭만으로 데이터 정상성을 보장할 수는 없습니다. freshness, 처리 건수, 중복과 품질 결과 같은 데이터 레벨 지표를 함께 운영해야 한다고 생각합니다.

### Q20. AI 분석 에이전트는 어떤 문제를 해결하나요?

**A.**

기존에는 현업의 분석 요청이 들어오면 데이터 엔지니어가 적절한 테이블을 찾고, 의미와 품질을 확인한 뒤 SQL과 차트를 만들어 전달했습니다. 이 과정에서 가장 어려운 부분은 SQL 생성보다 어떤 자산을 신뢰해야 하는지 판단하는 것이었습니다.

그래서 자연어를 바로 SQL로 변환하지 않고 OpenMetadata에서 설명, 소유권, 계보, 태그와 품질 정보를 검색해 후보 자산을 먼저 좁히도록 설계했습니다. 이후 Silver·Gold 자산을 우선 사용해 SQL 실행, Metabase 차트와 분석 보고까지 연결했습니다.

핵심은 LLM 자체보다 표준화된 데이터 모델과 검색 가능한 메타데이터를 먼저 마련했다는 점입니다.

### Q21. AI 에이전트의 잘못된 응답은 어떻게 통제하나요?

**A.**

에이전트가 자유롭게 운영 데이터를 변경하도록 하지 않습니다. 데이터 조회는 허용된 read-only 자산으로 제한하고, 선택한 자산과 생성 SQL, 실행 결과의 출처를 남겨 검토할 수 있게 해야 합니다.

장애 분석 에이전트도 자동 조치보다 영향 범위, 관측 근거, 원인 후보와 확신도를 포함한 처방전을 제공하고 최종 조치는 사람이 판단하도록 설계했습니다. 앞으로는 대표 질문과 장애 사례를 평가셋으로 만들고 자산 선택 정확도, SQL 실행 성공률, 근거 일치율을 지속적으로 측정해야 합니다.

### Q22. Data Part Lead로서 직접 한 일과 팀원이 한 일을 구분해 주세요.

**A.**

저는 플랫폼 전환의 방향과 핵심 아키텍처, 기술 선택 기준을 정하고 위험도가 높은 초기 구현을 직접 담당했습니다. Doris·SeaweedFS 전환, DuckDB 로그 ETL, OpenMetadata 도입과 같은 기반 설계가 여기에 해당합니다.

팀원이 확장 구현을 맡을 때는 공통 패턴과 운영 기준을 먼저 만들었습니다. 예를 들어 PyAirbyte 커넥터는 Dynamic DAG 패턴과 Bronze·Silver·Gold 책임을 정의한 뒤 팀원들이 소스를 확장할 수 있도록 했습니다.

리드 역할을 맡은 이후에는 제가 모든 코드를 작성하기보다, 팀원이 독립적으로 운영할 수 있는 표준과 리뷰 기준을 만드는 데 집중하고 있습니다.

### Q23. 가장 아쉬웠던 기술적 결정은 무엇인가요?

**A.**

초기 OpenMetadata 계보 연동에서 제품 API를 직접 호출하는 커스텀 방식을 선택한 점입니다. 당시 버전 충돌을 우회하고 빠르게 적용할 수 있다는 장점이 있었지만, 특정 제품의 API와 메타데이터 모델에 결합되어 장기 유지보수 비용이 생겼습니다.

이후 Airflow 3 전환 시 OpenLineage 표준 이벤트 기반으로 변경했습니다. 이 경험을 통해 단기적인 구현 속도뿐 아니라, 책임 경계와 교체 가능성을 기술 선택의 기준에 포함해야 한다는 점을 배웠습니다.

### Q24. 오픈소스 기여 경험이 있나요?

**A.**

오픈소스를 프로덕션에 도입하고 사내 환경에 맞게 확장·운영한 경험은 많지만, upstream 프로젝트에 반영된 PR 경험은 별도로 구분해서 말씀드려야 합니다. 내부 플러그인이나 커스텀 연동 개발을 오픈소스 기여라고 과장하지 않겠습니다.

대신 Airflow, OpenMetadata, Doris와 PyAirbyte를 운영하며 발견한 문제를 재현 가능한 형태로 정리하고, 앞으로 issue·문서·PR로 환원하고 싶습니다.

> **면접 전 보완:** 실제 공개 issue, PR, 문서 기여가 있다면 저장소·링크·기여 내용을 정확히 정리한다.

## 2. 컬리 예상 질문

### Q25. 왜 컬리인가요?

**A.**

컬리의 역할이 단순한 파이프라인 개발이 아니라 데이터 메시, Observability, FinOps와 운영 자동화를 함께 다룬다는 점이 제 경험과 잘 맞았습니다.

저는 비트망고에서 레거시 플랫폼 전환 이후 OpenMetadata 기반 계보·품질·소유권 체계를 구축했고, 이를 AI 분석과 장애 대응 자동화로 확장했습니다. 컬리는 이미 BigQuery와 AWS·GCP, 수백 개 파이프라인을 운영하고 있어 제가 해온 문제를 더 큰 규모와 다양한 환경에서 발전시킬 수 있다고 생각했습니다.

또한 채용 제안에서 플랫폼 전환과 거버넌스, AI 자동화 경험을 구체적으로 봐주셨기 때문에, 제가 기여할 수 있는 문제와 팀이 풀고 있는 문제가 명확하게 연결된다고 판단했습니다.

### Q26. BigQuery를 직접 운영한 경험이 부족한데 괜찮을까요?

**A.**

BigQuery를 프로덕션의 주 데이터 웨어하우스로 운영한 경험은 없습니다. 이 부분은 명확히 말씀드리겠습니다.

다만 대규모 분석 환경에서 데이터 분할, 스캔 범위, 사전 집계, workload 분리, 쿼리 비용과 사용자 패턴을 관리해 온 경험은 있습니다. Doris에서는 분산키, 파티션, materialized view, compaction과 노드 자원을 직접 관리했다면, BigQuery에서는 파티셔닝·클러스터링, materialized view, slot과 reservation, bytes scanned와 쿼터 관리로 운영 지점이 달라진다고 이해하고 있습니다.

입사 후에는 기존 쿼리와 비용 데이터를 통해 주요 workload를 분류하고, Doris에서 했던 최적화 가정을 BigQuery 실행 계획과 비용 모델에 맞게 다시 검증하겠습니다.

### Q27. 데이터 메시 플랫폼을 어떻게 구축하겠습니까?

**A.**

처음부터 조직 전체를 데이터 메시로 바꾸기보다 한두 개 도메인에서 데이터 제품의 최소 계약을 정의하겠습니다.

각 데이터 제품에 owner, schema, freshness SLO, 품질 규칙, 접근 정책과 변경 절차를 부여하고 중앙 플랫폼은 이를 등록·검증·관측하는 셀프서비스 도구를 제공합니다. 기술 메타데이터와 계보는 자동 수집하고, 비즈니스 정의와 품질 책임은 도메인이 관리하도록 나누겠습니다.

초기 성공 기준은 카탈로그 등록 수가 아니라, 소유자 없는 자산 감소, 장애 영향 범위 확인 시간, 데이터 문의와 중복 테이블 감소로 보겠습니다.

### Q28. 관리되지 않은 권한 체계를 어떻게 통합하겠습니까?

**A.**

먼저 현재 사용자, 서비스 계정, 그룹과 실제 사용 현황을 수집해 권한 인벤토리를 만들겠습니다. 이후 개인에게 직접 부여된 권한을 역할과 도메인 그룹 중심으로 전환하고, 개인정보 등급과 사용 목적처럼 단순 역할만으로 표현하기 어려운 조건에는 속성 기반 정책을 결합하겠습니다.

신규 권한은 최소 권한과 만료를 기본값으로 하고, 고위험 데이터는 승인과 감사 로그를 남깁니다. 사용되지 않는 권한은 바로 삭제하기보다 소유자 확인과 유예 기간을 거쳐 회수하겠습니다.

OpenMetadata의 소유권·분류 정보와 클라우드 IAM의 실제 권한을 연결하면 자산 맥락을 포함한 정책 검토가 가능하다고 생각합니다.

### Q29. CDC 파이프라인에서 중복과 순서 역전을 어떻게 처리하겠습니까?

**A.**

CDC 도구가 이벤트를 전달한다고 해서 최종 테이블의 exactly-once가 자동으로 보장되지는 않습니다.

이벤트에는 원천 primary key, transaction 또는 log position, 변경 시각과 operation type이 필요합니다. consumer와 sink는 key와 version을 기준으로 이미 반영된 이벤트를 식별하고, 더 오래된 이벤트가 나중에 도착하면 최신 상태를 덮어쓰지 않도록 해야 합니다.

초기 snapshot과 증분 CDC가 전환되는 지점에서는 누락과 중복 가능성이 있으므로 watermark 또는 log position을 기준으로 연결하고, 원천과 대상의 건수·checksum·핵심 지표를 지속적으로 대사하겠습니다.

### Q30. Airflow, NiFi, Kafka Connect, Flink의 역할을 어떻게 구분하나요?

**A.**

Airflow는 유한한 배치 작업의 의존성과 재시도, 백필을 관리하는 데 적합합니다. Kafka Connect와 NiFi는 소스와 sink 사이의 수집·전송을 표준화하는 데 강점이 있습니다. Flink는 지속적으로 들어오는 이벤트를 상태와 event time을 기준으로 처리해야 할 때 적합합니다.

동일한 변환을 여러 도구에 중복 구현하지 않는 것이 중요합니다. 단순 DB CDC 전달은 Kafka Connect나 DMS에 맡기고, 복잡한 상태 기반 실시간 집계는 Flink, 일 단위 모델 빌드와 검증은 Airflow로 구분하겠습니다.

직접 운영 경험이 없는 도구는 문법보다 장애·재처리·상태 소유권이라는 공통 기준으로 학습하고 검증하겠습니다.

### Q31. EKS에서 데이터 파이프라인을 운영한다면 무엇을 중요하게 보나요?

**A.**

데이터 작업은 일반적인 API 서버보다 실행 시간이 길고 메모리 사용량 변동이 크므로 requests와 limits를 실제 workload에 맞게 설정하는 것이 중요합니다. OOM이나 node eviction이 발생했을 때 작업이 어느 범위부터 재시작되는지도 데이터 멱등성과 함께 설계해야 합니다.

worker는 가능한 stateless하게 만들고 checkpoint와 처리 상태는 외부 저장소에 둡니다. secret과 service account는 작업별 최소 권한으로 분리하고, 로그·메트릭·이벤트를 연결해 pod 장애와 데이터 지연을 함께 확인할 수 있어야 합니다.

저는 DockerOperator 기반으로 ETL 실행 환경을 격리한 경험이 있으며, EKS에서는 이를 다중 노드 스케줄링과 자원 정책까지 확장해야 한다고 생각합니다.

### Q32. Data Observability를 구축한다면 무엇을 측정하겠습니까?

**A.**

네 계층으로 나누겠습니다.

첫째, 인프라 계층에서는 CPU, 메모리, 디스크, 네트워크와 컨테이너 상태를 봅니다. 둘째, 파이프라인 계층에서는 실행 시간, 성공률, retry, queue time과 consumer lag을 봅니다. 셋째, 데이터 계층에서는 freshness, volume, null, duplicate, schema drift와 분포 변화를 봅니다. 넷째, 사용 계층에서는 쿼리 빈도, downstream 영향도와 SLO 위반을 봅니다.

알림은 단순 실패보다 영향도를 반영해야 합니다. lineage와 ownership을 이용해 어떤 데이터 제품과 사용자가 영향을 받는지 확인하고 담당자에게 라우팅하겠습니다.

### Q33. Data FinOps 도구는 어떻게 설계하겠습니까?

**A.**

비용을 클라우드 계정 수준에서만 보지 않고 프로젝트, 도메인, 파이프라인, 사용자와 쿼리 단위로 귀속할 수 있어야 합니다.

BigQuery는 bytes scanned, slot 사용량과 reservation을, AWS는 EKS workload, 네트워크와 스토리지 비용을 태그와 실행 메타데이터에 연결하겠습니다. 정상 범위보다 스캔량이나 실행 시간이 급증하거나 사용되지 않는 예약 자원이 발견되면 이상으로 표시합니다.

절감액만 보여주기보다 비용을 줄였을 때 freshness와 성능 SLO가 어떻게 변하는지도 함께 보여줘야 합니다. 비용·안정성·확장성 사이의 의사결정을 지원하는 도구가 목표입니다.

### Q34. GenAI를 개발 워크플로에 적용한 경험을 설명해 주세요.

**A.**

Apple Silicon의 MLX 기반 로컬 LLM 환경을 만들고 GitLab hook과 연결해 코드리뷰와 릴리스 문서 작성을 보조했습니다. 또한 OpenMetadata를 탐색하는 데이터 분석 에이전트와, CMDB 관계 및 Prometheus·Elasticsearch·LibreNMS의 관측 정보를 이용하는 장애 분석 에이전트를 개발했습니다.

반복 작업을 모델에 맡기되 최종 실행 권한을 바로 주지 않은 것이 공통 원칙입니다. 에이전트는 근거와 결과를 제공하고 사람은 변경과 조치를 승인합니다. 컬리에서도 생성 속도보다 테스트, 출처, 권한과 재현 가능성을 포함한 워크플로를 만들겠습니다.

### Q35. AI 활용 문제해결 과제에서는 어떻게 접근하겠습니까?

**A.**

먼저 문제의 성공 기준과 제약을 제가 직접 정의하겠습니다. 이후 AI에는 전체 문제를 한 번에 맡기기보다 요구사항 분석, 대안 생성, 구현과 검토를 분리해 사용하겠습니다.

생성된 코드나 설계는 테스트와 반례로 검증하고, 사용한 가정과 수정 내용을 남기겠습니다. AI가 제시한 결과를 그대로 제출하는 것이 아니라, 어떤 부분에서 AI가 도움이 됐고 어떤 오류를 제가 발견해 수정했는지까지 설명하겠습니다.

## 3. 빗썸 예상 질문

### Q36. 왜 빗썸인가요?

**A.**

빗썸의 공고는 데이터 수집과 DW 연계뿐 아니라 누락, 중복, 정합성, 모니터링과 재처리를 핵심 업무로 명시하고 있습니다. 이는 제가 로그 파이프라인과 Airflow 백필, Data Quality as Code를 설계하며 집중해 온 문제와 맞닿아 있습니다.

가상자산 거래 데이터는 일반 분석 데이터보다 정확성, 감사 가능성과 복구 절차가 중요합니다. 지금까지 구축한 재처리와 계보·품질 경험을 금융 수준으로 발전시키면서, 거래와 정산이라는 새로운 도메인을 배우고 싶어 지원했습니다.

### Q37. 금융 또는 거래 데이터 경험이 없는데 어떻게 보완하겠습니까?

**A.**

금융·가상자산 도메인을 직접 운영한 경험은 없습니다. 따라서 도메인 규칙은 입사 후 가장 우선해서 학습해야 할 부분입니다.

다만 데이터가 틀렸을 때 원인을 추적하고 다시 만들 수 있는 구조는 도메인과 관계없이 중요합니다. immutable raw data, 처리 이력, partition 단위 재처리, source-to-target 대사와 lineage를 운영해 왔습니다.

빗썸에서는 여기에 주문·체결·입출금·정산의 상태 전이와 회계적 불변식을 학습하고, 단순 건수 비교가 아니라 금액 합계와 잔액 변화까지 검증하는 reconciliation을 설계하겠습니다.

### Q38. 주문·체결·정산 데이터를 DW에 적재한다면 어떻게 설계하나요?

**A.**

먼저 원천 이벤트를 변경하지 않는 형태로 보존하고, 각 이벤트에 business key, event time, ingestion time, sequence 또는 log position을 함께 저장하겠습니다.

정제 계층에서는 중복 제거와 상태 순서를 처리하고 주문, 체결, 입출금 같은 핵심 이벤트를 fact로 모델링합니다. 정산 계층에서는 주문 금액, 체결 금액, 수수료, 자산 이동과 잔액 변화 사이의 불변식을 검증합니다.

현재 상태 테이블만 유지하면 과거 변경을 추적하기 어려우므로 이벤트 이력과 최신 snapshot을 분리하겠습니다. 오류 데이터는 정상 데이터에 섞지 않고 quarantine하고, 재처리와 승인 이력을 남기겠습니다.

### Q39. 원천은 1,000만 건인데 DW에는 999만 건이라면 어떻게 조사하나요?

**A.**

전체 건수만 비교하면 어느 구간에서 누락됐는지 알 수 없으므로 범위를 단계적으로 줄입니다.

먼저 동일한 시간 기준과 완료 watermark를 사용했는지 확인합니다. 이후 날짜·시간·source partition 또는 key range별 건수를 비교해 누락 구간을 찾습니다. 해당 구간에서는 primary key 집합, min/max key, checksum과 금액 합계를 비교합니다.

수집 로그, offset, DLQ, retry와 sink commit 이력을 확인해 source, transport, processing, load 중 어느 단계에서 사라졌는지 판단합니다. 복구 후에는 동일한 reconciliation 검사를 다시 통과해야 완료로 처리합니다.

### Q40. 중복·누락·지연을 어떻게 탐지하나요?

**A.**

중복은 business key와 event version 또는 source offset의 유일성으로 확인합니다. 누락은 expected partition, 원천 대비 건수·checksum·핵심 합계와 sequence gap으로 탐지합니다. 지연은 event time과 ingestion time, 처리 완료 시간의 차이를 기준으로 freshness SLO를 측정합니다.

세 문제는 서로 연관될 수 있습니다. 재시도로 중복이 생기고, late event가 일시적인 누락처럼 보일 수 있기 때문에 허용 지연과 완료 watermark를 명확히 정의해야 합니다.

### Q41. Exactly-once를 어떻게 보장하나요?

**A.**

특정 메시징 시스템의 exactly-once 기능만으로 전체 파이프라인이 정확히 한 번 처리된다고 보지 않습니다.

source에서는 변경 이벤트를 고유하게 식별할 수 있어야 하고, consumer는 처리 상태와 offset을 일관되게 관리해야 합니다. sink는 business key와 version을 기준으로 idempotent upsert하거나, partition 단위 결과를 원자적으로 교체해야 합니다.

마지막에는 원천과 대상의 reconciliation이 필요합니다. 제가 목표로 하는 것은 ‘이벤트가 한 번만 전달됐다’는 보장보다, 여러 번 전달되거나 재실행돼도 최종 결과가 동일하고 검증 가능한 상태입니다.

### Q42. 순서가 뒤바뀐 이벤트는 어떻게 처리하나요?

**A.**

처리 도착 순서가 아니라 event time과 원천의 sequence 또는 version을 기준으로 판단합니다. 최신 상태 테이블에는 현재 version보다 오래된 이벤트가 도착해도 상태를 되돌리지 않도록 조건부 upsert를 적용합니다.

집계는 허용 지연을 기준으로 watermark를 운영하고, watermark 이후 도착한 late event는 보정 스트림이나 별도 배치로 반영합니다. 금융 데이터에서는 늦게 도착한 이벤트를 버리기보다 이력과 보정 결과를 모두 남겨야 합니다.

### Q43. 재처리 구조는 어떻게 설계해야 하나요?

**A.**

재처리 단위를 명확한 key로 정의해야 합니다. 날짜만으로 부족하다면 시간, source partition, shard와 서버 ID까지 포함합니다.

동일 key 재실행 시 기존 결과를 안전하게 overwrite하거나 merge하고, downstream은 실제 변경된 key만 다시 처리하도록 합니다. 대규모 백필은 실시간 workload와 queue·resource group을 분리하고 처리량을 제한합니다.

재처리 전후의 원천 건수, 대상 건수, 금액 합계와 품질 결과를 기록하고 누가 어떤 이유로 실행했는지도 감사 이력으로 남기겠습니다.

### Q44. Kafka consumer lag이 증가하면 어떻게 진단하나요?

**A.**

먼저 유입량이 증가한 것인지 소비 처리량이 감소한 것인지 분리합니다. partition별 lag과 message rate, consumer 처리 시간, rebalance와 오류율을 확인합니다.

처리량 저하라면 외부 API나 sink DB latency, serialization, GC, CPU와 네트워크를 확인합니다. 특정 partition에만 lag이 집중되면 key skew나 hot partition을 의심합니다.

consumer 수를 늘리기 전에 partition 수와 key 분포, sink가 추가 처리량을 받을 수 있는지를 확인해야 합니다. 긴급 복구와 근본 원인 개선도 구분해서 진행하겠습니다.

### Q45. Flink를 직접 운영하지 않았는데 스트리밍 업무를 할 수 있나요?

**A.**

Flink를 프로덕션에서 직접 운영한 경험은 없습니다. 다만 스트리밍에서 해결해야 하는 핵심 문제인 event time, 상태, checkpoint, 순서 역전, 중복과 sink 멱등성을 중심으로 학습하고 있습니다.

제가 Airflow와 DuckDB 배치를 설계할 때도 처리 key, 재시도, 실제 출력 범위와 downstream 이벤트를 분리했습니다. Flink에서는 이 개념이 지속 실행되는 operator state와 checkpoint, watermark로 확장된다고 이해하고 있습니다.

초기에는 기존 job의 운영 구조와 장애 사례를 먼저 익히고, 상태가 작은 비핵심 파이프라인부터 변경해 운영 경험을 확보하겠습니다.

### Q46. Spark와 Flink는 어떤 기준으로 선택하나요?

**A.**

단순히 배치는 Spark, 실시간은 Flink라고만 구분하지 않겠습니다.

유한한 대규모 데이터 처리와 다양한 분석 라이브러리, 기존 배치 생태계가 중요하면 Spark가 적합할 수 있습니다. 지속적인 이벤트 처리, 낮은 지연, event time과 큰 상태를 정확하게 관리해야 하면 Flink가 강점이 있습니다.

선택 시 허용 지연, 상태 크기, 데이터 순서, backfill 방식, 팀의 운영 역량과 기존 플랫폼을 함께 고려하겠습니다.

### Q47. Iceberg, Delta Lake, Hudi 경험이 있나요?

**A.**

프로덕션에서 세 table format을 직접 운영한 경험은 없습니다. 현재는 SeaweedFS에 gzip 원본과 Parquet 분석 데이터를 저장하고 Doris에 적재하는 구조를 운영했습니다.

이 구조는 파일 단위 재처리는 가능하지만 transaction log, snapshot, time travel과 row-level update를 표준 table format 수준으로 제공하지는 않습니다. Iceberg는 다양한 엔진과의 호환성과 대규모 메타데이터 관리, Delta는 Spark 중심 생태계와 강한 통합, Hudi는 incremental processing과 upsert에 강점이 있다고 이해하고 있습니다.

빗썸에서는 기존 엔진 호환성, CDC·upsert 비중, 운영 도구와 lock-in을 비교한 뒤 PoC로 선택하겠습니다.

### Q48. 데이터 품질 오류가 발생하면 파이프라인을 중단해야 하나요?

**A.**

오류의 영향도에 따라 다르게 처리해야 합니다.

거래 금액 불일치, 핵심 키 중복, 필수 이벤트 누락처럼 잘못된 데이터가 사용되면 금전적 영향을 만들 수 있는 오류는 downstream 반영을 차단해야 합니다. 지표 분포의 경미한 변화처럼 정상 비즈니스 변화일 가능성이 있는 검사는 경고와 검토 대상으로 둘 수 있습니다.

차단 여부, 허용 임계치와 예외 승인 주체를 데이터 계약에 명시하고, 예외를 적용하더라도 원래 실패 결과와 승인 이력을 지우지 않겠습니다.

### Q49. 새벽에 적재 지연이 발생했고 재시도하면 중복 위험이 있다면 어떻게 대응하나요?

**A.**

우선 SLA 영향과 현재 처리 상태를 확인합니다. 실행 여부만 보고 전체를 재시도하지 않고 마지막으로 commit된 partition, offset 또는 batch key를 확인합니다.

sink가 key 기반 upsert나 partition 교체를 지원하면 해당 범위부터 멱등하게 재처리합니다. 멱등성이 보장되지 않는 구조라면 임시 테이블에 재처리 결과를 만들고 기존 결과와 비교한 뒤 교체합니다.

복구 후 원천 대비 건수와 금액 합계, 중복 키를 검증하고, 지연 원인과 재처리 범위, 사용자 영향을 incident 기록으로 남깁니다.

### Q50. 대규모 백필이 실시간 파이프라인에 영향을 주지 않게 하려면 어떻게 하나요?

**A.**

백필과 실시간 작업의 실행 자원을 분리하고 백필 처리량을 제한합니다. Airflow pool이나 별도 queue, 엔진의 workload group을 사용해 우선순위를 구분할 수 있습니다.

대상 테이블에 직접 대량 쓰기보다 shadow table 또는 임시 partition에 적재하고 품질과 reconciliation을 통과한 뒤 교체하는 방식이 안전합니다. consumer lag, DB load와 BI latency를 관측하면서 허용 범위를 넘으면 백필을 자동 중지할 수 있어야 합니다.

## 4. 성과 수치 검증 질문

### Q51. 관리 공수를 70% 줄였다는 근거는 무엇인가요?

**A.**

기존에는 유사한 DAG마다 코드를 수정하고 리뷰·배포해야 했지만, 메타데이터 기반 DAG Factory 도입 후에는 설정 변경만으로 생성과 수정이 가능해졌습니다.

다만 70%가 정식 time tracking을 통한 수치가 아니라 변경 전후의 대표 작업 시간을 바탕으로 산정한 값이라면 그 점을 명확히 말씀드리겠습니다. 중요한 결과는 파이프라인 수가 증가해도 코드베이스와 배포 횟수가 같은 비율로 증가하지 않게 된 것입니다.

> **면접 전 보완:** 변경 전후 신규 DAG 생성 시간, 월 배포 건수, 장애 건수를 확인한다.

### Q52. API 연동 리소스를 80% 절감했다는 근거는 무엇인가요?

**A.**

기존에는 API별 인증, pagination, 증분 수집과 schema 처리를 직접 구현했습니다. PyAirbyte 전환 후 지원되는 소스는 커넥터 설정과 검증 중심으로 바뀌어 개발 범위가 줄었습니다.

다만 커넥터가 모든 유지보수를 제거한 것은 아닙니다. 버전 변경, schema drift와 커스텀 소스는 여전히 운영이 필요합니다. 80% 수치는 대표 연동 사례의 작업량 비교인지 전체 평균인지 구분해서 설명하겠습니다.

> **면접 전 보완:** 자체 구현 사례와 PyAirbyte 적용 사례 각각의 실제 소요 시간을 확인한다.

### Q53. 인프라 구축 비용을 100% 절감했다는 표현은 정확한가요?

**A.**

신규 서버 구매 비용이 발생하지 않았다는 의미입니다. 기존 장비를 재배치했기 때문에 신규 하드웨어 CAPEX를 피했습니다.

하지만 기존 서버의 전력, 디스크 교체, 운영 인력과 마이그레이션 비용이 사라졌다는 뜻은 아닙니다. 따라서 면접에서는 ‘신규 하드웨어 구매 비용을 발생시키지 않았다’고 표현하겠습니다.
